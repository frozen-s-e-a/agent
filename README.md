## 自建 Agent 方案

面向公司内部部署的本地模型，在**短期内无法更换更强模型**的前提下，通过自建 agent loop 和客户端，尽量抵消模型能力不足（思考深度低、多重任务易漏、有效上下文有限）带来的影响，并以审计工作为首个落地场景。

### 核心原则

- **把"想全、想对"从模型搬到代码结构里**：规划、执行、验证分离，模型每次只做一个小而明确的动作。
- **代码算数，模型写判断**：大数据量由程序处理，模型只看汇总表和异常清单。
- **按有效上下文做预算**：标称 128k，按实测有效长度（初始 32k）规划。
- **结果可验证、可追溯**：每步由代码强制校验，每个数字可追溯到源数据。

### 建议落地顺序

1. 建立评估基准：收集 10~20 个真实失败任务，记录失败环节
2. 低成本优化：工具输出截断、JSON 容错/约束解码、流式与进度展示
3. 核心循环：规划与执行分离、每步验证、任务清单
4. 审计数据层：标准数据结构 + 主流财务系统导入适配
5. 首批审计程序：日记账测试、银行流水核对、往来款项
6. 底稿输出层与更多程序、行业配置

### 首版目标

**首版完整迁移原工具箱全部业务功能，后续版本再做功能优化。** 原先 A/B 分批发布的范围划分取消；按模块开发只是施工顺序，首版交付必须全量验收。此前已确认的UI、账号/配额和执行展示调整保留。

[原工具箱全功能迁移清单](docs/原工具箱全功能迁移清单.md)记录模块、模板、Skill、未知入口和逐项兼容验收；文件数不等于业务功能数。

### 实施原则

- 主选 Electron、React/TypeScript、Node.js Harness、Python worker；小批量按预算在 Python 内处理，DuckDB/Parquet 负责大批量分析，SQLite 负责应用元数据。
- 优先验证并复用固定版本 DeepSeek Harness，通过适配层隔离上游接口；保留来源和许可证声明。
- 审计功能允许通过反编译、静态分析和原程序行为测试参考实现，转化为可复核的规则与自主维护源码。
- 先建立原行为基线与兼容执行底座，完整迁移全部业务；规则、算法和业务模板优化留到首版之后。双模式、恢复和原件保护仍是首版工程要求。
- 源码在 src，测试在 tests，研究原始产物在 research/legacy，编译与测试输出在 build/artifacts，运行和业务数据不进入 Git。

参考上游：[DeepSeek Harness 固定提交](https://github.com/deepseek-ai/deepseek-harness/tree/5dda764ed3aa172535a7967b06ff95d9cbfe536a)。兼容性以本项目实测清单为准。
