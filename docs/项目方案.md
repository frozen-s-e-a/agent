# AI助手项目方案

版本：v0.4
更新：2026-09-09
状态：设计基线。当前已建立开发目录和 Git；本文件中的功能、模块与测试均属于计划。

## 1. 项目目标和产品边界

构建以对话为入口、以项目文件夹为工作范围的 Windows 审计 AI 应用。用户可以直接提问，也可以创建项目、选择文件夹、运行审计规则并生成底稿。结果应能回到原始文件、工作表、行或 PDF 页定位。

首版取消原程序的功能列表、旧项目管理页、账号与项目数量配额、独立运行过程页。执行记录进入对话；模型、参数、扩展和资源预算进入独立设置。项目数量不设置商业配额；内存、磁盘与任务并发受实际资源控制。

本轮补充的核心设计：

- 审计实现可以研究原程序：源码阅读、反编译、原生二进制分析和行为测试按文件类型选择，研究成果经过验证后转化为可维护实现。
- 同一应用提供轻量本地与大批量落盘两种设计，共用规则、工具和证据接口，支持自动选择及手动指定。
- 小批量在独立 Python 进程预算内快速处理，不强制建分析库；大批量从导入、计算到导出采用分批、落盘和有界资源设计。
- 两种模式首版均可在本机运行；远程执行仅预留接口，切换大批量模式不自动上传数据。

用户原始需求与新增需求的编号及验收见[需求边界与验收](需求边界与验收.md)。

### 1.1 首版全功能迁移，后续业务优化

首版目标调整为：完整迁移原工具箱的全部实际业务功能，包括审计计算、数据处理、文件操作、资料查询、模板、辅助工具和原 AI 助手可用能力。原 A1–A4 首版、B1–B3 后续的范围划分取消；开发可以按模块分批，但首版发布前必须全部收口。

“保留所有功能”与此前已确认的产品调整同时执行：旧功能列表页面、旧项目管理页面、账号和项目配额、独立运行过程页按原要求移除或重构；原页面承载的业务能力全部保留，通过对话命令、可搜索工具入口和参数卡片使用。不能因为界面入口改变而让某项功能只能靠模型猜测才能调用。

首版以原行为兼容为优先：核对输入格式、参数/默认值、规则口径、输出结构、模板、公式、宏及必要外部依赖。原工具箱已有的特殊格式或外部功能不能因为难迁移就排到后续。发现的功能一律进入全功能迁移总账，未确认用途或未通过验证的项目不能计入完成。

首版允许为迁移所必需的接口重构、进程隔离、恢复、双模式执行和原件保护；不借迁移之名新增审计规则、调整阈值、改变抽样方法或重新设计业务模板。涉及业务结论的优化单独记录到后续版本。

当前文件盘点仅是线索，完整功能基线还必须核对原入口、子功能、参数分支、Skill和模板之间的关系。见[原工具箱全功能迁移清单](原工具箱全功能迁移清单.md)。

## 2. 推荐技术栈与选择理由

|层次|主选|职责|选择理由|代价与控制|
|---|---|---|---|---|
|桌面外壳|Electron|窗口、原生文件夹选择、生命周期、安装更新|与 DeepSeek Harness Desktop 路线接近，便于承载 Web 对话界面|安装体积及内存开销需要实测，计算不能堵塞主进程|
|界面|React + TypeScript，Vite 构建|对话、项目、操作卡片、Token、设置|组件可拆分，前后端接口可做类型检查|使用分页/虚拟列表，禁止把完整数据集送进 renderer|
|Agent 运行环境|Node.js + TypeScript|运行 Harness、扩展管理及工具调度|适配上游 Node/Cordis 插件生态，便于流式事件处理|同步重计算交给独立 worker|
|Harness 实现|固定版本 DeepSeek Harness + 本项目适配层，P0 验证后锁定|模型循环、上下文、工具调用、会话与取消|优先复用已有执行能力，业务变更集中在扩展点|上游处于开发预览，必须固定提交和回归升级|
|业务计算|独立 Python worker|文件解析、数据转换、审计规则执行、导出|便于利用和验证原工具箱同类数据处理逻辑|独立打包运行时；限制并发和内存，保留结构化错误|
|批量分析|DuckDB + Parquet，按需使用 Arrow 批次|多文件扫描、筛选、聚合、关联、排序及中间结果|分析与存储不要求整表转成 Python 对象|SQL 和算子同样需要预算；不保证所有查询都能自动溢写|
|轻量本地处理|pandas + openpyxl；PDF 解析适配器|单个或少量文件的预算内转换、规则计算、模板生成|启动路径简单，不强制经过 Parquet 和分析库|入场先估算内存；触及预算时转入大批量模式|
|复杂格式处理|按需 PDF/OCR/Office 适配器|逐页解析、公式与模板保真|将特殊格式需求从数据规模选择中分开|实际引擎与分发依赖在 P0 锁定|
|应用元数据|SQLite|项目、设置、任务索引、缓存目录和投影游标|本地部署简单，支持事务|不存百万行结果正文；单一服务管理写入与迁移|
|会话记录|追加式事件日志，优先沿用上游格式|重建模型历史、对话卡片和用量|执行历史可以恢复、追踪|仅已提交事件可恢复；流式中间片段不承诺零损失|
|扩展|Cordis/dsh 适配、MCP、SKILL.md|工具接入、外部系统、业务工作流|支持后续渐进扩展|三者能力不同，分别管理权限、版本和健康状态|
|工程|pnpm workspace、Python 锁文件、Git、类型/集成测试|模块依赖、可复现构建与验证|接口和依赖清晰，源码与构建产物分离|依赖精确版本在 P0 实测后固定，不盲目使用 latest|

Node.js 是运行环境，Harness 是其上运行的执行系统。使用 Node.js 并不自动获得恢复、审批、上下文压缩和插件能力。

Electron/Node、Python、DuckDB 的具体补丁版本在 P0 根据 Windows x64 构建和兼容性试验锁定。Python 3.12 可作为旧模块研究环境基线，正式 worker 版本根据依赖测试确定；研究环境不与新应用运行环境混用。

Electron 的进程分离依据其官方设计；DeepSeek Harness Desktop 采用独立 Node 子进程与管道通信。这里复用架构思路，不宣称目前已经完成集成。[Electron 进程模型](https://www.electronjs.org/docs/latest/tutorial/process-model)、[上游 Desktop](https://github.com/deepseek-ai/deepseek-harness/blob/5dda764ed3aa172535a7967b06ff95d9cbfe536a/apps/desktop/README.md)

### 2.1 原工具箱技术基线

研究对象为桌面 SW审计工具箱 目录。文件名和依赖只证明存在相关组件，不证明具体算法正确，也不能仅凭目录名确认版本为 1.8.6。

|已观察到的文件|可确认的事实|尚不能据此确认|
|---|---|---|
|_internal/python312.dll|随程序带有 Python 3.12 运行时|完整编译和发布流程|
|_internal/PySide6|包含 Qt/PySide6|所有窗口的线程安全性|
|ai_assistant/backend.pyd、chat_ui.pyd|AI 后端与聊天模块存在|其实现已能可靠恢复|
|nanobot_core/runner.pyd、tools、memory.pyd、skills.pyd|包含 Agent、工具、记忆、技能模块|每项实际能力和异常覆盖率|
|pandas、NumPy、DuckDB、PyMuPDF、python-calamine|包含数据分析及文件解析组件|各业务实际采用哪个解析器|
|subject_clean、detailed_table、jet_test、monthly_analysis 等模块|存在可研究的审计功能入口|规则公式、边界、速度和准确率|

.pyd 是 Windows Python 原生扩展形式之一。Cython 可以生成 .pyd，但后缀本身不能证明编译器，更不能保证还原成原始 .py。当前不把闪退归因于 Python 或 Qt；需要复现、日志和进程级诊断。

### 2.2 其他路线与当前取舍

|路线|适合的方向|本项目决定|
|---|---|---|
|Tauri + Web UI + Rust|重视桌面外壳体积、已有 Rust 维护能力|保留为备选；同时打包 Node/Python 后的实际收益需要测量|

这些是不同目标下的技术路线，不是行业排名。Tauri 使用系统 WebView；AI SDK 聚焦 AI 集成；LangGraph 提供持久工作流能力。[Tauri](https://tauri.app/concept/process-model/)、[AI SDK](https://github.com/vercel/ai)、[LangGraph](https://langchain-ai.github.io/langgraph/index.html)

## 3. 上游复用策略

固定参考提交：5dda764ed3aa172535a7967b06ff95d9cbfe536a。

主选路径是复用该版本中适合本项目的 Harness 服务和插件接口，通过 src/harness-adapter 对外提供稳定接口。对话项目关联、审计工具、批量任务、文件事务和业务规则由本项目实现。修改上游必要时使用小范围补丁，记录原因、来源、测试和更新方法。

P0 必须证明以下能力可在目标 Windows 环境独立运行：

1. 精确依赖构建、打包与无系统 Node/Python 的启动。
2. 模型流式回复、工具调用、取消、持久化恢复与 usage 事件映射。
3. 审计工具注册和 Python worker 调用不需要侵入核心循环。
4. 插件安装失败回滚及升级兼容检查可被桌面壳控制。
5. 长任务不会阻塞界面，也不会因通用工具超时误判正常批处理失败。

如果公开接口不能满足核心边界，先形成差异和成本 ADR，再选择受控 fork 或最小自有 Harness。该选择不改变业务模块接口，不提前承诺上游插件全部兼容。

上游 README 标明开发预览，LICENSE 标明 MIT；复用时保留适用声明并记录第三方依赖，不能把“开源”理解为所有依赖和品牌均可任意重分发。[上游说明](https://github.com/deepseek-ai/deepseek-harness/blob/5dda764ed3aa172535a7967b06ff95d9cbfe536a/README.md)、[LICENSE](https://github.com/deepseek-ai/deepseek-harness/blob/5dda764ed3aa172535a7967b06ff95d9cbfe536a/LICENSE)

## 4. 进程架构和模块边界

~~~mermaid
flowchart TD
  UI["React 对话/项目/设置"] <-->|受限桥接与事件| SHELL["Electron 主进程"]
  SHELL <-->|有界管道协议| HOST["Node Host + Harness Adapter"]
  HOST --> HARNESS["固定版本 Harness"]
  HOST --> META["SQLite 元数据 / 会话日志"]
  HOST --> SCHED["任务调度与资源预算"]
  SCHED <-->|任务 ID / 进度 / 引用| WORKER["Python Worker 池"]
  WORKER --> ENGINE["DuckDB / Parquet / 解析与审计规则"]
  HOST --> EXT["插件 / MCP / Skills"]
  HOST --> FILES["文件授权与结果发布"]
  ENGINE --> STAGE["受控输入和暂存输出"]
  FILES --> OUT["用户项目文件夹"]
~~~

图中是责任域，Electron 自身还包含 renderer 等进程，不能理解为“全应用只有三个进程”。Python、插件或解析器进程退出时，由 Host 记录失败并恢复管理状态；UI 不直接执行文件或 shell 操作。进程隔离本身不等于操作系统沙箱。

|源码模块|唯一主责|公开边界与约束|
|---|---|---|
|src/client|呈现对话、项目、设置和结果预览|只消费 API，不拼接 shell、不读密钥、不持有全量数据|
|src/host|桌面生命周期、受限桥接、后台启动|不实现审计公式|
|src/contracts|IPC、事件、工具、数据集 schema|作为交换格式真相，TS/Python 均校验|
|src/harness|会话执行入口和本项目执行策略|通过 adapter 使用上游能力|
|src/harness-adapter|上游事件/API 映射|上游类型不泄露进审计域|
|src/projects|项目根目录、策略和会话关联|不维护账号配额，不更改原文件|
|src/conversations|会话索引、事件投影、时间线查询|不重复保存另一份权威模型历史|
|src/settings|非敏感配置、修订号、凭据引用|secret 单独存储，仅写入/替换，不回显|
|src/file-ops|根路径校验、文件版本、最终发布事务|接收暂存结果；覆盖前检查源版本|
|src/task-scheduler|排队、并发、预算、取消、恢复|与模型循环独立，管理后台审计任务|
|src/execution-router|选择轻量/批量执行策略|依据体量、格式、算子和预算，记录路由原因|
|src/datasets|数据集清单、版本和血缘索引|保存位置与统计，不经 IPC 搬整表|
|src/audit-worker|Python 任务入口和文件/计算适配|向调度器报告状态，不依赖 UI|
|src/audit-domain|纯 Python 业务规则与证据模型|计算可脱离模型和窗口测试|
|src/usage|usage 规范化、去重、费用估算|上下文估算与实际消耗分离|
|src/plugin-manager|安装、启停、升级、回滚|与配置页、运行工具区分|
|src/mcp|连接与工具桥接|调用也经过工具策略|
|src/skills|SKILL.md 发现、描述加载和工作流入口|不能绕过工具权限或自行提升身份|

目录为模块规划；空目录或文档不代表功能实现。跨模块允许依赖其公开接口，禁止深层导入他方实现。

## 5. 产品交互

### 5.1 对话与项目

左侧包含新建对话、独立会话、项目列表、设置。项目下含多会话；创建时选择名称和根目录，可配置默认模型、启用技能及输出目录。

独立对话无需项目；操作文件前选择或授权目录。切换项目即切换工具作用域，不继承上一项目的文件授权。重设项目根目录需要停止或明确处理运行任务，并保留旧结果的原始定位记录。

每次审计流程按“识别输入 → 映射字段/选规则 → 选择处理模式 → 执行 → 展示异常与证据 → 导出”组织。处理模式默认自动，可手动选择“轻量本地”或“大批量”；超过资源预算时给出具体原因并建议切换，不让用户选择强制突破进程上限。已授权的目录内读取和生成新结果直接执行；需要用户决定的覆盖、删除、范围扩大等在对话中提出具体确认。

### 5.2 执行记录

工具卡片包含名称、脱敏参数、状态、耗时、输入/输出引用、异常和重试操作。大任务显示阶段、已处理文件/行数、失败数量、预算、取消和恢复入口；详细技术日志由展开项查看。

时间线记录实际动作，不编造模型内部推理。大量进度合并刷新，明细通过分页查询；不把每一行数据变成对话消息。

### 5.3 Token 交互

参考 Desktop 的三层：单轮 Usage 展开面板、输入区上下文占用、会话累计统计；设置中的用量页作为本项目增加的聚合视图。

- 展示 total/input/output、缓存读写和 reasoning 等供应商实际提供字段，未知显示“未知”。
- 请求与重试以 requestId/attemptId 去重；父子运行按明确归属聚合。
- reasoning 若属于 output 的子集则不重复相加；缓存字段按供应商语义规范化，保留原值。
- 上下文压力属于估算，不能累计成账单用量。费用只有在价格及计费口径明确时估算并标注日期。
- 中断请求可能无法取得最终用量，标记“统计不完整”；本地计算行数增加不必等比例增加 Token。

[上游 Usage 组件](https://github.com/deepseek-ai/deepseek-harness/blob/5dda764ed3aa172535a7967b06ff95d9cbfe536a/packages/client/ui-chat/src/client/chat/TurnUsagePanel.tsx)、[Token meter](https://github.com/deepseek-ai/deepseek-harness/blob/5dda764ed3aa172535a7967b06ff95d9cbfe536a/docs/subsystems/token-meter.md)

### 5.4 设置

独立设置包含：模型与服务地址、凭据、默认项目策略、文件权限、资源与缓存、Token 预算、插件管理、MCP、Skills、审计规则版本、诊断导出。企业网关/模型 API 凭据与本应用账号功能分开。

## 6. Harness 稳定性设计

### 6.1 状态和恢复

Agent turn 与后台数据任务采用两个关联状态机。数据任务状态为：

~~~text
queued → preparing → running → validating → publishing → succeeded
                     ↘ pausing → paused → queued
                     ↘ cancelling → cancelled
任意活动阶段 → failed / interrupted / recovery_required
~~~

暂停只发生在可保存检查点的阶段；不承诺把任意底层 SQL 或解析调用冻结到任意一行。重启恢复检查输入版本、规则版本、已提交分片和最终输出，完成的非幂等操作不能自动再做一次。

### 6.2 日志和存储真相

- 会话历史以持久化 session log 为准；SQLite 保存索引与已投影 seq，可重建。
- 项目、设置、任务排队和检查点由各自明确的元数据表拥有；不能声称所有数据库都是可丢弃缓存。
- 大结果存 Parquet/文件，事件只记引用、摘要、hash 和数量。
- 接口消息含 protocolVersion、requestId、sessionId、taskId、type、payload；有大小限制、超时、取消、背压和去重。
- 原始 usage、受保护的模型上下文与脱敏诊断分开保存；保留证据所需内容并限制访问，密钥不进入其中。

### 6.3 文件发布

解析和计算先生成暂存文件；file-ops 核验授权、路径、版本和完整性后发布。单文件在支持的本地文件系统同卷替换，并先保留可恢复备份；网络盘采用先本地计算再验证发布，不能假设具有相同原子语义。

多文件输出使用 run manifest 记录完成状态，全部验证后标为完成；崩溃时保留中间状态，不把部分输出冒充完整报告。符号链接、junction、大小写及用户更改文件造成的路径/版本竞争都需要测试。

### 6.4 故障处理

|异常|处理|
|---|---|
|模型限流/网络错误|有上限的退避重试，显示尝试记录；不自动重复已写文件|
|上下文过长|压缩已记录的可摘要内容、按需取证；固定保留关键规则与证据引用|
|工具参数错误|返回可读校验错误，不启动 worker|
|解析器崩溃/worker OOM|隔离失败任务，记录退出信息；从受支持检查点恢复|
|磁盘不足/文件锁定|暂停发布、保留检查点，允许释放空间/改名后继续|
|插件/MCP 失联|隔离连接失败，不令整个应用启动失败|
|模型生成错误 SQL|受控数据集和预算下校验/执行；禁止任意文件、扩展安装和网络副作用|

允许在审计模块范围选择反编译参考路线。先盘点实际源码、模板和入口，再识别 PyInstaller 归档、.pyc 字节码、.pyd 原生扩展；按类型使用解包、反汇编/反编译和行为测试。将还原得到的逻辑标成“待验证”，通过合成样例和手算预期确认后形成规则规范。

## 8. 数据处理双模式设计

同一套应用、项目、审计规则、结果格式和证据链，提供两条执行路径。两种模式首版都在本地运行，差别是数据流、存储和任务调度方式。

|维度|轻量本地模式|大批量模式|
|---|---|---|
|目标场景|单个或少量工作簿、少量 PDF、一次性小任务|跨文件明细、百万级记录、大量文档、复杂全局关联|
|计算路径|独立 Python worker + 预算内 pandas/解析器|分批导入 + Parquet + DuckDB + 有界 worker|
|中间存储|以预算内存为主，必要时保存阶段产物|显式持久数据集、分片和磁盘暂存|
|恢复粒度|从已完成工具步骤恢复，失败步骤重算|从文件/分片/查询阶段检查点恢复|
|交互|简洁工具卡片与直接预览|同类卡片增加队列、阶段、文件/行数和资源信息|
|主要代价|规模有限，复杂操作可能放大内存|预处理和磁盘成本，需预算与缓存治理|

~~~text
同一任务入口 → 输入探测 + 规则计划 + 资源估算
  ├─ 轻量本地 → 预算内解析/计算 → 校验 → 暂存/发布
  └─ 大批量   → 分批读取 → Parquet → DuckDB → 分片结果 → 校验/发布
                    两条路径共用规则版本与证据格式
~~~

路由默认自动，也允许项目默认值和单次手动选择。决定依据包括总行列数、解压后估算大小、文件数、算子类型、可用内存及磁盘。不能只按文件大小或“是否 Excel”判断。

轻量模式触及预算时，终止当前未提交步骤并用同一输入快照切换批量执行；保留历史事件，不重复发布结果。批量转轻量只在下一任务或阶段边界重新计划。

共同底线：金额与代码类型一致、输入版本固定、失败行有清单、全量/抽样状态清楚、结果可追溯。两条路径必须用同一测试集对比结果，不允许维护两套含义不同的审计规则。

大批量路径额外要求全局算子正确、磁盘溢写、预算调度、断点续跑、分页预览和分卷导出；禁止全量数据进入模型上下文或 renderer。小批量则保留简单快速的文件工作流，不要求用户先理解数据库或配置复杂集群。

场景、路由阈值草案、恢复与性能矩阵见[数据处理双模式方案](数据处理双模式方案.md)。DuckDB 的流式执行与溢写适合大路径，但不免除应用的预算与异常管理责任。[DuckDB 内存管理](https://duckdb.org/2024/07/09/memory-management)

## 9. 插件、MCP 与 Skills

插件负责可执行能力，MCP 负责外部工具协议，Skills 负责领域操作说明和流程；不能将三者统称为可以随意运行的提示词包。

- 插件管理支持添加、查看来源/权限/兼容版本、启停、升级、卸载、失败回滚。安装采用固定版本和 hash、暂存、健康检查、切换、journal；依赖脚本按明示策略处理。
- dsh/Cordis 插件优先按上游包声明解析，本项目补充兼容与权限元数据，不强迫所有上游包重写成私有格式。支持范围由兼容矩阵声明。
- 前端插件扩展需要与客户端构建兼容；首版只加载匹配的界面贡献，不承诺任意 npm 包都能热插入 UI。
- MCP 先实现 stdio/Streamable HTTP 的工具桥接；如果原工具箱实际提供 resources/prompts 或其他可用能力，也必须列入首版兼容项，不能因上游适配器暂不支持就取消。新增且原来没有的协议能力才进入后续扩展。连接有超时、重连、工具命名空间和最小环境变量集合。
- Skills 保留原来可用的包布局和 references/scripts 等能力，并兼容常见 SKILL.md 导入；项目可附审计元数据，缺少私有 manifest 不应阻止纯文本 Skill 导入。脚本执行仍走工具策略。
- 后台插件崩溃不影响已启用的内置审计任务。将任意本机可执行扩展隔离成进程并不自动获得文件/网络沙箱，不能在 UI 中夸大权限保证。

[上游 MCP 范围](https://github.com/deepseek-ai/deepseek-harness/blob/5dda764ed3aa172535a7967b06ff95d9cbfe536a/packages/mcp/mcp-client/README.md)

## 10. 实施阶段与交付判断

首版是“全功能迁移版”；第二阶段起才是业务优化版。以下 P0–P4 全部属于首版，不允许将未迁移业务移入“后续优化”以提前结束首版。

|阶段|核心交付|退出条件|
|---|---|---|
|P0 全量盘点与技术验证|原功能/子功能/参数/模板总账、样例基线、上游适配与双模式验证|文件线索全部关联或有明确非业务用途；盘点遗漏持续补入|
|P1 产品壳与调用入口|对话、项目、设置、明确可调用的工具/参数卡片|已迁移业务在新UI中可直接定位，不依赖模型猜测|
|P2 兼容执行底座|Harness、worker、路由、两种数据模式、Token、文件事务、扩展接口|兼容能力与故障测试通过，支撑全部业务工作包|
|P3 全业务迁移|M01–M16及后续盘点发现的业务项，逐项研究、迁移、对照|原功能、选项、模板和输出全覆盖；未明用途和依赖阻塞有闭环|
|P4 全量验收与首版发布|完整工作流、新旧对照、双模式、外部依赖、安装恢复回归|总账中所有首版业务项通过，未解决缺项为零|
|第二阶段及后续 业务优化|规则增强、算法改进、模板重设计、体验与性能专项、新功能|以首版兼容基线为对照，独立版本、测试和变更说明|

插件注册与MCP/Skill兼容在P0/P2就验证，不能留到发布前才发现原功能无法接入。开发内部可以先演示已完成模块；演示包和不完整测试包必须标明覆盖范围，不能称为全功能首版。

业务优化排期不阻止必要的首版工程修复，工程修复也不能成为擅自改变规则的理由。具体验收与兼容例外处理见[需求边界与验收](需求边界与验收.md)、[原工具箱全功能迁移清单](原工具箱全功能迁移清单.md)。

当前不承诺完成工期或实测性能数值。需要先获得全量盘点与依赖验证结果，再形成逐模块估算；范围完整不等于目前已经完成迁移。
