# JET 核心逻辑提取与验证

日期：2026-10-10。目标：取得可独立重写的核心判断、计算公式和处理流程。本轮为核心逻辑提取试验，未把研究代码接入客户端，也未完成其余旧 MCP 功能的迁移。

## 1. 结论及完成范围

**可行性已经获得实际验证。** 原安装包中的 JET 是 Cython 原生扩展。通过函数入口定位、反汇编、运行时常量恢复和合成数据对照，取得了条件解析逻辑以及 11 类计算方法，覆盖 13 个内置特征。按测出的行为写了一份自有 Python 实现，计算时无需加载旧 EXE、旧 `.pyd` 或旧安装目录。

这份实现位于 [jet_reference.py](research/progress-20261010/core-logic-20261010/jet_reference.py)，用于解释和验证核心规则。它有意保留测出的旧行为，包括部分值得纠正的边界行为；不能据此认定旧审计规则的业务口径必然正确。

|验证|范围|结果|
|---|---|---|
|条件解析|260 个“函数 × 字段 × 条件”案例；其中 8 个返回“没有条件”，其余进行 5,040 次逐行布尔比较|通过|
|内置特征计算|13 个内置特征，每个 8 行，104 次逐行比较|通过|
|特征边界|重复行、指定重复字段、小数尾数、负数取模、空值相等、无效日期等 7 个案例，41 次逐行比较|通过|
|原 EXE 的实际 MCP 输出|4 条规则，比较实际 XLSX 的命中行 ID、规则命中次数与汇总页|全部相符：21 次规则命中，涉及 11 条不同源记录|

总计 **5,185 次核心结果逐行比较**，另有 4 条规则的原 EXE 端到端输出比较。布尔和文本严格比较；特征浮点数以 `rel_tol=1e-12`、`abs_tol=1e-9` 比较，不是逐位比较。

实验环境为 CPython 3.12.14、pandas 3.0.1。完整条件和特征覆盖使用原 JET 核心模块搭配这个研究环境；原 EXE 验证覆盖上述 4 条规则，不能把它扩大成所有旧运行时行为都已验证。

## 2. 怎么从安装包拿到核心规则

本轮采用如下步骤，不要求恢复原作者的完整源码工程：

1. 根据 MCP 注册映射找到 `modules/jet_test/jet_test_execute.pyd`，再追到 `_core.pyd` 和 `_builtin.pyd`。
2. 静态读取 PE 的方法定义表，定位 `_check_single_item`、`_check_condition`、`FeatureEngine.apply_tool`、`process_data_chunk` 等入口。
3. 用官方 Rizin 便携工具反汇编。Cython 的参数包装函数与实际计算函数分开记录。
4. 在独立研究进程中加载原核心模块，取得函数签名、内置配置及反汇编引用的字符串常量。没有启动旧 GUI，没有读取真实账套或旧账号配置。
5. 给原函数输入合成数据，记录判断结果；依据这些结果与调用分支编写自有实现。
6. 不加载原模块运行自有实现，对记录下来的预期逐行比较；再调用原 EXE 的 MCP，以实际成果 XLSX 做一次完整执行对照。

## 3. 条件解析的实际语义

### 3.1 单个条件

|条件|原核心实际行为|
|---|---|
|`>N`、`<N`、`>=N`、`<=N`、`!=N`|先数值化再比较；去掉英文千分位逗号，无法数值化的值按 0 处理|
|裸数字，例如 `1000`、`-0.01`|数值等于；支持负号和普通小数，`.01`、`1e3` 不属于这套数字语法|
|`=1000`、`#1000`|转成文本后精确等于 `1000`，与裸数字的数值相等不同|
|普通文本|忽略大小写的字面包含；会转义正则特殊字符|
|`^文本`|区分大小写的前缀匹配|
|`!^文本`|不以指定文本开头|
|`!文本`|忽略大小写的“不包含”|
|`#文本`、`=文本`|精确文本相等，字段内容不自动去首尾空格|

数值表达式对应的字符串常量为 `^(>=|<=|!=|>|<|=)\s*(-?\d+\.?\d*)$`；裸数字对应 `^(-?\d+\.?\d*)$`。虽然第一条表达式识别 `=`，运行行为仍把 `=1000` 作为精确文本比较；研究实现保留这个结果。

例子：`1000` 能匹配 `1,000`、`1000` 和 `1000.0`；`=1000` 只匹配转换为文本后恰好是 `1000` 的值。无效文本在裸数字 `0` 条件下可以命中，这属于原数值清洗行为，不能把它理解为源数据确实为零。

### 3.2 同一字段里的多个条件

中英文逗号都作为分隔符。实际组合为：

```text
字段掩码 = （所有正向条件取 OR） AND （所有排除条件取 AND）
没有正向条件时，前半部分为 TRUE。
数字比较 !=N 归入正向条件组，不归入文本排除条件组。
```

|表达式|实际含义|
|---|---|
|`调整,回款`|包含调整，或者包含回款|
|`!调整,!回款`|既不包含调整，也不包含回款|
|`调整,回款,!回款`|包含调整或回款，并且不包含回款|
|`^6,^7,!^1`|以 6 或 7 开头，并且不以 1 开头|
|`>22,<7`|大于 22，或者小于 7|
|`>=6,<=8`|大于等于 6，或者小于等于 8；不是区间限制|
|`!=0,!=1`|不等于 0，或者不等于 1；因此所有转换后的数值都会满足|

不同字段条件在已验证的规则执行中取 AND，例如“借方金额 >7”与“科目编码以 6001 开头”必须同时满足。

### 3.3 没有条件与空值条件

- 整个条件为 `None`、NaN、空字符串或只有空格时，`_check_condition` 返回 `None`，含义是没有谓词。
- `[空]` 判断真实缺失值或纯空白字符串；`![空]` 判断其相反。文本 `nan`、`None` 不等于真实空值。
- `是`、`否` 判断精确的中文文本，不自动把 Python `True/False` 转成这两个词。
- 分隔出来的空片段不会被删除。`7,,8` 会保留一个空的字面包含条件，从而全匹配；新产品需要在配置校验中明确处理，不能让用户无意建立这种条件。

完整观察保存在 [condition-observations.json](research/progress-20261010/core-logic-20261010/condition-observations.json)。

## 4. 13 个内置特征的计算方法

这些特征由 11 种工具计算：余数和组内计数分别用于两个内置特征。

|特征|计算方法|已测出的边界|
|---|---|---|
|跨月编制|两个日期的 `(年×12+月)` 相减后取绝对值|不考虑日；缺失日期的差额填 0|
|凭证月份|日期转成 datetime，取 month|无效/缺失日期填 0|
|制单小时数|日期时间取 hour|无效/缺失时间填 0|
|是否周末|星期序号 ≥5 返回“是”，否则“否”|无效日期返回“否”|
|借方余数|清洗借方金额；0 替换为缺失，再对参数求余|负数按 Python/pandas 模运算；不自动按分取整|
|贷方余数|与借方余数相同，输入改为贷方|金额 0 的特征结果是缺失值|
|尾数后3位|每个金额取绝对值、截去小数、转整数文本，再取后 N 位；多个非空结果以 `\|` 拼接|0 返回空串；0.01 返回“0”；10 返回“10”，不补成“010”；相同尾数不去重|
|摘要长度|字段转文本后计算字符数|保留首尾空格；研究环境下真实缺失仍为缺失|
|凭证差额|按指定凭证键分别求借贷合计，取二者差的绝对值并回填到该组每一行|缺失分组键的结果为缺失；分组键默认含凭证日期、类型、编号|
|科目频率|按科目编码分组后计数，回填每一行|真实缺失分组值不计入普通组|
|制单人频率|按制单人分组计数|空字符串和空格是不同组；真实缺失结果为缺失|
|行重复|按全部列或配置的指定列查重复，`keep=False`|首次出现的重复行也标“是”；真实缺失值参与重复判定|
|制单审核一致|两列先将缺失填空，再转文本比较，返回“是/否”|双方缺失或空字符串与缺失可以判一致；空格不等于空串；数字 1 与文本“1”可以一致|

内置配置与实际观察分别在 [native-builtins.json](research/progress-20261010/core-logic-20261010/native-builtins.json)、[feature-observations.json](research/progress-20261010/core-logic-20261010/feature-observations.json)。

## 5. 执行流程与成果口径

本轮用原适配器与核心函数测出了以下契约：

1. MCP 的 `features`、`rules`、`column_mapping`、`settings` 接口字段是 JSON 字符串，进入适配器后再解析成对象。
2. 特征对象转换为包含“辅助列名称”“计算工具”“来源列名 (必须修改)”“参考值/参数”的 DataFrame。规则对象转换为“规则名称”“是否执行”和各条件字段的矩阵。
3. **空特征表会导致本次测试中的规则处理不产生结果。** 两条有明确命中数据的规则在 `features: []` 下仍返回成功、0 命中；加入“凭证月份”这个特征后产生预期记录。独立实现应把“只测试原字段”作为明确支持的模式，或者明确校验拒绝，不能沿用这种无提示结果。
4. 可用字段的条件得到布尔掩码；规则中的不同字段取 AND；每条规则返回命中行，并添加“公司名称”和“涉及规则”。
5. 原成果文件含“目录”“汇总”和每条规则的工作表。在本次实际结果中，汇总页按规则拼接命中行；同一源记录触发多条规则会重复出现。

本次 4 条规则的命中次数依次为 3、8、8、2；`total_hits=21` 和汇总页 21 行一致，但只有 11 条不同的源记录。因此新界面应区分“规则命中次数”和“涉及源记录数”，并以源行 ID 展示一条记录命中了哪些规则。

本轮没有完整验证多主体拆分、目录遍历、多文件去重、模糊列匹配、所有前置条件报错、全部自定义工具参数和 XLSX 样式布局。不能把核心计算对照通过写成整个 `jet_test_execute` 已完成正式迁移。

证据：[适配器到核心的试验](research/progress-20261010/core-logic-20261010/pipeline-summary.txt)、[原输出逐规则对照](research/progress-20261010/core-logic-20261010/mcp-output-verification.json)。

## 6. 必须登记的规则来源差异

原 `_builtin.pyd` 的内置配置和 Excel `JET配置表.xlsx` 是两套实际存在的规则来源。此前仅凭二者不一致判断 Skill 说明错误，依据不充分；MCP 内置配置本身就与 Skill 所写的部分条件一致。

|位置|MCP 内置配置|Excel 模板|
|---|---|---|
|期末收入突击|凭证月份为 12、**借方金额** >1,000,000、科目编码以 6001/6051 开头|月份与科目条件相同，但金额条件在**贷方金额**|
|准备类借方异常|借方金额 >0、科目编码以 1231 开头，另有 `alias_subject` 元数据|除金额与编码条件外，矩阵还有“科目名称包含坏账准备”|
|规则名称|33 条记录，33 个不同名称；借/贷方向分别命名|33 条记录，规范化括号后只有 31 个不同名称；“期末费用调整”“重大估计调整”各重复两次|

不能选一份文件直接宣称取得了全套唯一业务规则。迁移时应为每条规则记录来源、稳定 ID、适用入口和版本；对于借贷方向等业务差异，应在正式规格中明确采用哪一套。

另外，原“凭证月份”把无效日期变成 0，而原“日期无效”规则使用 `[空]`。在已测出的核心行为中，这条规则无法据此识别已变成 0 的月份。此类旧规则问题应单独登记，不能为了对照一致而把它当成正确的审计判断。

证据：[两套来源差异与重复记录](research/progress-20261010/core-logic-20261010/rule-source-differences.json)。

## 7. 独立复验与后续迁移

只复验已重写逻辑时，不需要旧工具箱：在装有 pandas/numpy 的 CPython 环境中，执行研究目录的 `verify_reference.py` 即可。它读取已保存的合成输入和预期结果，调用自有 `jet_reference.py`，没有导入旧模块。

调用原模块和原 EXE 的脚本仅用于继续研究及生成对照基线；它们有明确的旧目录依赖，不能加入正式安装包。生产迁移应把核实后的规则放入 `src/audit-domain`，接入自有任务执行器，并完成输入、成果、依赖与打包验收。

下一批应按“接口 → 实际核心模块 → 规则规格 → 自有实现 → 原成果对照”继续。银行核对已定位到多层匹配函数，月间分析已定位到金额方向与分组计算函数；这些目前只是定位/静态线索，尚未获得本文件这种独立重写验证。IPO 下载还要核实请求参数、分页、文件筛选和重试流程。其余 63 项入口的状态继续见 [独立迁移清单](独立迁移逐项清单-20261010.md)。

全部 63 个入口的原文件及核心函数线索已经完整核对，见 [63 项核心逻辑提取范围与进展](63项MCP核心逻辑提取范围与进展-20261010.md)。本文件只记录先行的 JET 验证，不限制整体提取范围。
