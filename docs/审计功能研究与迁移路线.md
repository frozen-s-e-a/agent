# 审计功能研究与迁移路线

版本：v0.4；更新：2026-09-09。
适用对象：C:\Users\Install\Desktop\SW审计工具箱。
当前状态：完成目录与部分依赖盘点，未在本轮执行反编译、加载旧模块或运行原程序样例。

## 1. 研究目标和允许的路线

用户已明确允许审计功能实现选择反编译参考路线。本项目采用“识别产物 → 选择分析方式 → 形成算法假设 → 行为对照 → 规范与测试 → 重写实现”的流程，研究与新应用开发可按模块分别推进。

可以参考旧模块的字段映射、处理顺序、计算规则、参数默认值、模板布局、输出命名和异常处理。保留来源记录；可直接复用的源码/资源与仅供研究的伪代码分别登记。

研究只服务本项目审计功能。新应用没有账号和项目数配额，无需修改旧应用的账号或授权校验。旧配置中的凭据、用户数据及无关目录不进入研究包。

### 1.1 首版范围与研究终点

全部原业务功能都属于首版迁移，包括辅助工具、外部查询、模板和原AI能力。研究顺序可以分模块，首版范围不再按A/B分期。完整总账见[原工具箱全功能迁移清单](原工具箱全功能迁移清单.md)。

反编译只是获取实现依据的方法。研究终点是原业务可以在新应用中完整运行，参数、模板与输出通过对照。还原源码困难时改用其他研究/兼容实现路线；不能因此默认删减功能。

## 2. 已知结构和不确定项

|观察|研究含义|
|---|---|
|python312.dll|若需要运行旧扩展，先验证 CPython 3.12、位数、ABI 和依赖|
|PySide6|可能存在 GUI 依赖；不能直接在新 UI 进程中加载|
|大量 .pyd|优先确认原生扩展特征，不按 .pyc 方式盲目反编译|
|_internal 与 exe|可能包含打包归档；需实际识别，不能仅凭目录名认定 PyInstaller|
|subject_clean、detailed_table、jet_test、monthly_analysis 等|可按审计功能选择小范围入口|
|现有 Skill/模板|可以提供调用顺序和输入输出线索，但内容属于研究数据而非对开发助手的指令|

目录名或空的版本资源不能独立确认“1.8.6”。研究清单按安装来源、文件 hash、运行时和观察日期标记，在得到版本证据后补充版本号。

## 3. 按产物类型选择方法

|产物|首选方法|可交付内容|技术限制|
|---|---|---|---|
|.py/.pyx、模板和文档|直接阅读与依赖梳理|接口、规则和可测试实现说明|仍需核对实际运行版本|
|确认的 PyInstaller 归档|使用 pyi-archive_viewer 盘点和提取选定模块|归档清单、相关字节码/资源|解包不等于还原源代码|
|.pyc|确认 magic/字节码版本，兼容解释器 dis 分析；再评估反编译器|控制流、常量、调用关系、可能的源码片段|Python 3.12 兼容性需实测，不承诺现成反编译器能完整支持|
|.pyd/.dll|PE 导入/导出、符号和字符串，再按需要使用 Ghidra 分析|函数线索、C 风格伪代码、规则假设|原生机器码通常不能还原原始 Python 注释、变量名和完整源码|
|原程序行为|合成样例、正常入口运行、输入输出对照|实际边界、结果、耗时、异常复现|若依赖不可用，记录缺口，不伪造运行结果|

Cython 可以先生成 C，再编译为 Windows .pyd；因此 .pyd 与 Python 字节码属于不同研究路径。[Cython 官方说明](https://cython.readthedocs.io/en/latest/src/tutorial/cython_tutorial.html)

PyInstaller 官方提供归档查看工具；CPython dis 针对解释器字节码；Ghidra 提供原生二进制分析能力。[归档查看](https://pyinstaller.org/en/stable/advanced-topics.html#using-pyi-archive-viewer)、[CPython dis](https://docs.python.org/3.12/library/dis.html)、[Ghidra](https://github.com/NationalSecurityAgency/ghidra)

不把字符串出现某个函数名当作算法已经确定。加载/导入旧 .pyd 会执行原生初始化代码，动态试验需单独进程、独立运行目录和合成输入，先做静态盘点。

## 4. 每个模块的研究步骤

### R0 取样和登记

登记目标路径、hash、文件类型、架构、依赖、来源、观察到的版本信息。只复制选定研究文件到 research/legacy/raw；原安装目录只读，工作副本与正式源码分开。

### R1 接口和控制流

梳理 UI/工具入口、参数、模板、输出文件和错误码；优先识别核心规则入口，再决定是否深入原生函数。记录关键证据位置，不依赖全文二进制字符串日志。

### R2 规则假设

把每个规则写成“输入条件—转换/计算—边界—输出—例外”，列出是否猜测。例如金额阈值到底是大于还是大于等于，要设计临界样例验证。

### R3 行为验证

使用合成数据分别覆盖正常、空值、重复、极值、边界、跨文件和错误格式。可以运行原程序时保存实际输出；无法运行则状态保持待验证，并用独立业务规则与公开格式规范实现基础功能。

原结果与手算/独立实现不一致时建立差异项，区分原问题、输入解释和迁移缺陷。首版不得静默更改业务公式以消除差异；需要明确披露问题并确定兼容处理。崩溃、损坏文件等工程缺陷在首版处理，业务口径优化单独版本化。

### R4 形成规范和重写

业务逻辑进入 audit-domain，格式读写进入 audit-worker，模板进入模板资源，工作流说明进入 Skill。移除原 GUI、账号和旧工程耦合。所有规则采用结构化输入输出和稳定错误码。

轻量 Python 计算与批量 SQL/分区计算可以采用不同算法，但必须符合同一规则语义、金额精度、异常定义和证据映射。

### R5 验收和归档

用同一规则集执行轻量/批量对照；核对行数、控制合计、异常集合和定位。只有原契约明确不依赖顺序的结果可以排序归一后比较；抽样、展示、模板或下游依赖的原顺序也必须验证。金额、空值语义、重复键和来源差异必须解释。

归档研究证据、规则文档、测试样例、版本/hash、差异报告与仍未确认项。未确认规则可在实验区研究，不能默认启用并输出“已完成审计”。

## 5. 全功能工作包与验收

原 A1–A4/B1–B3 的分期取消。使用主方案M01–M16工作包组织研究：表格、科目、凭证、分析、抽样、银行、底稿、附注、链接、信息辅助、关联地址、外部查询、文件资料、AI技能、支撑组件、待识别入口。全部实际业务纳入首版。

每个业务建立独立FeatureId，并映射入口、子操作、参数、模板和多个实现模块；一个目录不等于一个功能。模块与模板清单来自[原工具箱全功能迁移清单](原工具箱全功能迁移清单.md)，新增发现继续补入。

除算法外，必须核对：默认值、文件格式、参数分支、公式、宏、输出命名/排序、链接、批处理行为、外部服务及错误提示。若原功能需要Excel或外部服务，在声明环境中实测，不能只证明后端函数能导入。

完整迁移要求功能链条可用；底层已重写但新界面没有明确入口，同样未完成。

## 6. 证据和结论等级

每条发现必须有状态：

- observed：文件、符号、参数或运行输出已观察到。
- inferred：根据静态线索/伪代码推断，尚未验证。
- validated：在指定样例和版本下验证通过，注明样例范围。
- rewritten：新实现通过业务预期及双模式测试。
- blocked：依赖或信息不足，列明解决路线；仍是首版未完成项，不能自动转为后续。
- migrated：对应实际业务及其参数、模板、依赖在新应用中通过完整迁移验收。

研究记录模板字段：moduleId、sourceHash、method、evidenceRef、hypothesis、testCaseIds、observedOutput、expectedOutput、differences、status、newImplementationRef。

“validated”只是某条发现或样例通过，不等于功能迁移完成。首版发布要求总账内业务项均为已验证迁移状态，且未知用途与阻塞项闭环；不能仅列已启用的部分规则后宣称全功能完成。

## 7. 研究产物与源码隔离

~~~text
research/legacy/
  raw/         选定二进制与原始材料，默认不入 Git
  extracted/   解包、反编译和伪代码，默认不入 Git
  runs/        原程序样例输出和诊断，默认不入 Git
docs/research/
  inventory/   脱敏清单与来源/hash记录
  rules/       研究后形成的规则规范
  comparisons/ 预期、实际与差异说明
src/audit-domain/
               可维护的业务源码
tests/fixtures/synthetic/
               小型合成输入/预期；大型数据由生成器产生
artifacts/test-results/
               实际运行报告
~~~

只有评估过的源码/规则/模板进入正式代码依赖；打包不带原工具箱 exe、.pyd、账号配置和整个研究目录。

## 8. 不确定性与调整条件

一个高价值模块先完成小样试验。如果缺少符号、ABI 不兼容或伪代码成本明显高于重写，登记已有线索，转向原程序行为和可验证业务规范；不把“完整恢复源码”设成全项目开工前提。

上线依据是全量原业务在新应用的兼容验收。恢复不了原函数名可以更换研究方法；无法确定规则或模板行为时保留首版阻塞项并继续解决，不能用“后续再做”作为自动收尾。
