# DeepSeek Harness 接入实测

日期：2026-10-17。

**依据：**
- dsh `0.2.1-rc.2`（npm `@deepseek-ai/dsh`），在 Linux 上实际运行；
- 本分支的 `harness/` 与 `src/audit-mcp/`；
- 自动测试：Harness 10 项、审计工具 MCP 服务 8 项，全部通过。模型用的是 OpenAI 格式的假模型服务，**还没有接真实企业模型**。

---

## 结论

- **底座可用。**用户只填地址和 Key 的接法、关闭外发、审计工具挂成 MCP 服务、取消、续跑、动作确认、追问、卡片，都在假模型下跑通了。
- **[接口约定](接口约定-20261017.md) 1.1 的两项定了：**
  1. **宿主用 SDK 协议连 Harness**，但把 dsh 自带的 SDK 服务换成我们的桥接插件。协议不变，补上取消、确认、追问、卡片和流式片段。取消直接停这一轮，不用结束进程。不用 ACP。
  2. **卡片回答由宿主请求 `card/answer` 直接送给等待中的编排插件。**原暂定的"带标记的消息 + `agent/pre-step` 拦截"实测不可行：插件在工具调用里等卡片时，消息只能排在收件箱里，等工具返回后才会被取出，回答永远送不到。
- **还剩企业环境的验证。**验证脚本已写好，命令见第十节。

---

## 一、版本

- 固定 `0.2.1-rc.2`（2026-10-17 发布），`harness/package-lock.json` 锁住全部 615 个依赖。

## 三、模型接法

- **适配器：**pi-ai 适配器，协议 `openai-completions`，路由名 `enterprise`。dsh 原生 DeepSeek 适配器只认 Anthropic 格式，不用。
- **用户填的：**地址和 Key。模型名由宿主从 `/models` 列表里选（接口约定 `settings` 已有"多个时选择"）。
- **地址：**去掉末尾斜杠和误填的 `/chat/completions`。要不要补 `/v1` 由连接测试决定：先试原样，再试补 `/v1`。
- **Key：**只放进 Harness 子进程的环境变量，配置文件里没有。
- **请求按最保守的方式发：**不发 `store`、不发 `reasoning_effort`、系统提示用 `system` 角色、输出上限用 `max_tokens`。企业网关支持哪些，等验证报告出来再放开。
- **128K：**
  - 上下文窗口 131072，输出上限 8192；
  - 压缩余量从默认 65,536 改为 12,288，阈值 0.8；
  - 约 10.5 万 token 开始压缩（默认配置下约 4.9 万就开始）。
- **思考字段：**先按不带思考的模型处理（`reasoningEfforts: false`）。企业模型如果返回思考内容，验证后再开，并确认回传方式。

## 四、外发

| 外发项 | 默认去向 | 处理 |
|---|---|---|
| 遥测 | `dsh-otel-collector.deepseeksvc.com` | 关闭 `otel`、`session-telemetry-otel` |
| 会话日志随请求上传 | 随模型请求的 `dsh_session_log` 字段 | 关闭 `session-log-deepseek`、`deepseek-llm-api-extensions` |
| 联网搜索、网页抓取 | `api.deepseek.com` 等 | 关闭 `web`、`web-search-deepseek`、`web-deepseek-api`、`web-fetch-http`、`tool-web` |
| DeepSeek 账号、官方模型 | `api.deepseek.com`、`platform.deepseek.com` | 关闭 `deepseek-account`、`llm-deepseek`、`llm-deepseek-account` |
| 插件安装 | npm 源 | 关闭 `plugin-manager` |
| 自动更新 | — | 只在桌面版里，`sdk` profile 没有 |

**怎么验证的：**
- 外连检查预加载到 Harness 进程，启动、初始化、跑完一整轮（模型调用审计工具再回复），记录里只有一次连接：本机的假模型。测试里有断言。
- 模型请求里没有 `dsh_session_log` 字段。
- `bridge/status` 返回实际生效的插件列表。宿主据此生成接口约定 4.11 的 `privacy.status`，不用写死。

**限制：**
- 外连检查只覆盖 Node 进程。审计工具的 Python 进程靠 `network_disabled` 运行（`transport.py` 的 `local_only`，只放行模型地址）。
- 现有工具里 6 项要联网（公告、三个交易所 IPO、注协查询、汇率），默认不提供给模型。

## 五、模型能用的工具

- **能用：**57 项审计工具（`mcp__audit__<工具名>`）、`ask_user_question`（追问）、`todo_write`、`skill`（只加载应用自带的 `harness/skills`）。
- **拿掉的：**shell、文件读写和搜索、改工作目录、后台任务、代码执行（`run_code`、`workflow`）、自由派生子 Agent、目标、计划模式、MCP 资源读取。
- 子 Agent 的运行时还在，编排插件可以按设计第三节起子 Agent，只是模型自己不能随意派生。
- 项目目录里的 `AGENTS.md`、技能目录不读：那是用户资料，不当作指令。

## 六、接口约定 1.1：宿主怎么连 Harness

| | dsh 自带 SDK | ACP | SDK 协议 + 我们的桥接插件 |
|---|---|---|---|
| 发消息、事件流、续跑 | 有 | 有 | 有 |
| 取消一轮 | 没有，只能结束进程 | 有 | 有（`session/cancel`） |
| 动作确认 | 没有 | 只有允许一次、拒绝 | 有，带工具名和调用编号 |
| 模型追问 | 没有 | 没有 | 有 |
| 编排插件的卡片 | 没有 | 没有 | 有 |
| 流式片段 | 没有，只有落盘事件 | 有 | 有（`assistant.stream`） |

**选第三种。**桥接插件在 Harness 进程里，替换 `sdk` profile 的 `sdk-jsonrpc-server`：
- 原有方法原样交给 dsh 的 SDK 服务类，兼容 dsh 的 SDK 客户端。
- 新增的请求和通知列在 `harness/README.md`。

**取消：**
- `session/cancel` 停止这一轮，会话可以继续发消息。
- 测试里这一轮的结束原因是 `aborted`。

**续跑：**
- Harness 进程被强行结束后，新进程用 `session/resume` 续上同一会话，之前的历史都在。测试覆盖。
- 这一条保留给崩溃恢复用，不再作为取消的手段。

**一个进程服务一个项目：**
- dsh 的 MCP 调用不带会话信息，审计工具服务无法按会话区分项目。
- 所以审计工具的访问范围按进程定：宿主打开项目时启动一个 Harness，切换项目时换进程。
- 会话日志放在同一数据目录，按会话编号续跑。
- 启动到初始化完成约 2 秒（含审计工具服务）。

## 七、接口约定 1.1：卡片回答怎么送回

**实测（测试"桥接请求直接送达等待中的插件……"）：**
1. 测试插件注册一个工具，调用时出一张卡片并等待回答。
2. 卡片发出后，宿主按原暂定方案把回答作为一条带标记的用户消息发进会话。
3. 等 1.5 秒：消息没有进入会话，插件拿不到回答。
4. 原因：dsh 只在步骤之间取收件箱，工具没返回前不会进入下一步，`agent/pre-step` 也就不会触发。
5. 改用 `card/answer` 后，回答立即送到插件，工具返回。之前排队的那条消息这时才被取出，作为普通用户输入交给了模型。

**做法：**
- 编排插件调用 `ctx.auditCards.open(agent, card, signal)`，等到回答（`{ card, action, edits, note }`）。
- 桥接插件发 `card.opened` 通知，宿主收到 `card.answer` 命令后转成 `card/answer` 请求。
- 这一轮被取消时卡片自动撤回，发 `card.closed`，带 `withdrawn: true`。测试覆盖。

**等待中的卡片不落盘：**
- Harness 进程退出后，未答的卡片随之消失。
- 编排插件从节点检查点续跑时要重新出卡，编排线的检查点设计要覆盖这一点。

## 八、需要接口约定跟着改的地方

1. 1.1 两项按第六、七节定。
2. 4.8 与 Harness 的对应表：
   - `message.delta` 来自桥接插件的 `assistant.stream`，不是 `session.event`；
   - 动作确认卡对应桥接插件的 `approval.request`，不是 Harness 原生事件直接转发。
3. 一个 Harness 进程只服务一个项目（第六节）。宿主切换项目时换进程，前端不受影响。
4. 内置审计工具在工具事件里的名字是 `mcp__audit__<工具名>`，`system` 填"审计工具"。
5. 现有 63 项工具的结果：
   - 金额是浮点数，不是十进制字符串（2.2）；
   - 产出写在 `outputs/<任务编号>/`，不是 `输出/<任务编号>/`（2.6）。
   
   这些旧工具先不改。审计工具线按 `audit-tools/1` 写新工具时按约定来。
6. 外部 MCP 服务（4.10）的落法：
   - 宿主为用户添加的服务生成一个额外配置层，每个服务一条 `dsh-mcp-client` 配置，启动时用 `--patch` 叠上；
   - `sideEffect: mutating` 的工具名写进 `confirmTools`，调用时走动作确认。

- **Windows 实机：**还没在 Windows 上跑过。PowerShell 已关闭；路径都用 `path` 模块拼接，应不受影响，验证脚本会一并检验。

## 十、企业模型验证（最后做）

在能连企业模型的 Windows 电脑上：

```bat
git clone -b claude/harness-integration-jy3eu0 https://github.com/frozen-s-e-a/agent
cd agent\harness
npm ci
set AUDIT_LLM_API_KEY=<你的 Key>
node tools\verify-enterprise.mjs --url <模型地址> --model <模型名> --python <python.exe 路径>
```

- 需要 Node ≥ 22.19；Python 需要 pandas、openpyxl。
- 加 `--context` 会再测实际上下文窗口，较耗 token。

**脚本做两件事：**
1. **直接探测接口：**
   - 模型列表、地址要不要补 `/v1`；
   - 普通回复、流式、流式用量；
   - 工具调用格式，以及工具结果回传；
   - `json_schema` / `json_object` 输出约束；
   - 有没有思考字段、`developer` 角色。
2. **用 Harness 跑一个小任务：**
   - 模型调用审计工具，从样例表格提取两列，再回答结果；
   - 同时检查除模型地址外有没有任何外连。

脚本生成 `verify-report-<日期>.json`，报告里不含 Key。根据报告调整配置层的兼容参数。
