# 04 上下文窗口与预算策略

## 128k 够不够

**128k 不算少**，属于当前开源/本地模型的主流水平，对单阶段任务、单模块产出完全够用。"上下文小"的体感通常来自以下原因，需逐项排查：

| 原因 | 排查方式 |
|---|---|
| 部署时被截短 | 检查推理框架实际生效的最大长度参数（vLLM `max_model_len`、Ollama `num_ctx`、llama.cpp `-c` 等），默认值可能只有 4k~32k |
| 有效上下文远小于标称值 | 很多模型超过 30k~50k 后召回和推理质量明显下降，量化后更严重 |
| 客户端塞得太满 | 冗长 system prompt、未截断的工具输出、全量历史 |

## 预算原则

- **按有效上下文做预算，不按标称窗口**：初始按 32k 规划，用真实任务测出质量拐点后调整。
- **各部分设上限**：system、任务清单、当前步骤输入、本步历史、检索内容分别限额（默认值见 `03-agent-loop-pseudocode.md` 的 `CONFIG`）。
- **超限裁剪顺序**：先压历史（旧往返压成摘要），再压检索内容，最后才动当前步骤输入。
- **工具结果先压缩再入上下文**：日志保留错误附近、文件保留头部和命中片段、检索结果取 top-k，并注明"已截断，可按行号/关键词再取"。
- **固定前缀不变**：便于推理服务的前缀缓存命中。

## 如何测有效上下文

1. 准备一组任务，在不同上下文长度下（如 8k / 16k / 32k / 64k / 100k）分别运行。
2. 记录关键信息召回率（"大海捞针"式插入事实再提问）和任务完成质量。
3. 取质量明显下降前的长度作为 `context_window` 的工作值。

## 审计场景的量级参考

128k token 约相当于 10 万汉字左右（视分词器而定）。一家中型企业一年的序时账动辄几万到几十万行，**原始数据不可能、也不应该进入上下文**，必须由代码处理，模型只看汇总结果和异常清单（见 `05-audit-agent-architecture.md`）。
