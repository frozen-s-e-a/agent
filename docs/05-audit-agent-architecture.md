# 05 审计 Agent 通用架构

## 定位

不承担整个审计工作，而是让审计人员可以把**某阶段的某项工作**或**某个模块的底稿**交给 agent 完成，重点覆盖数据量大、人工操作费时费力的板块。

**核心原则：代码算数，模型写判断。** 数据进工具，不进上下文。

---

## 一、四层架构

```
┌──────────────────────────────────────────────────────┐
│ 输出层   底稿模板（Excel/Word），数字由代码填写，      │
│          模型只写分析说明与结论，每个数字可追溯到源行  │
├──────────────────────────────────────────────────────┤
│ Agent 层 理解需求 → 映射审计程序 → 确认参数 →          │
│          规划/执行/验证循环 → 解读结果 → 撰写说明      │
├──────────────────────────────────────────────────────┤
│ 程序库   每个审计程序是一个工具：                      │
│          输入标准数据 + 参数 → 输出结果表 + 异常清单   │
├──────────────────────────────────────────────────────┤
│ 数据层   各财务系统导出 → 统一标准结构                 │
│          （通用性的关键，换客户只需适配导入）          │
└──────────────────────────────────────────────────────┘
```

### 数据层标准结构（初版）

| 表 | 主要字段 |
|---|---|
| 科目表 | 科目编码、科目名称、级次、方向、标准科目映射 |
| 科目余额表 | 期间、科目、期初、借方发生、贷方发生、期末 |
| 序时账 | 凭证日期、凭证号、行号、科目、摘要、借方、贷方、对方科目、制单人、审核人、录入时间、辅助核算 |
| 辅助核算明细 | 往来单位、部门、项目、个人等维度 |
| 银行流水 | 账户、交易日期、对方户名、对方账号、收入、支出、余额、摘要 |
| 报表 | 报表项目、期初、期末、本期、上期 |

### 程序库接口约定

```python
def procedure(data: StandardData, params: dict) -> ProcedureResult:
    """
    ProcedureResult:
      summary_table   汇总表（进入模型上下文）
      exceptions      异常清单，每条含：规则 ID、命中原因、源表、源行号/凭证号、金额
      full_output     完整结果文件路径（不进上下文，写入底稿）
      checks          勾稽校验结果（通过/失败及差异）
    """
```

## 二、优先覆盖的高工作量板块

| 板块 | 主要内容 |
|---|---|
| 数据导入与勾稽 | 余额表、序时账、报表三者核对；期初期末衔接 |
| 日记账测试 | 全量筛查异常分录：周末/节假日、期末大额、整数金额、异常摘要、非常规对方科目、手工/冲销分录 |
| 银行流水核对 | 流水与账面双向核对；大额资金流向追踪 |
| 往来款项 | 账龄分析、函证清单生成、回函差异汇总、替代程序 |
| 抽样 | 货币单位抽样、分层抽样、样本清单与底稿生成 |
| 截止测试 | 期末前后收入、成本、费用的跨期识别 |
| 重新计算 | 折旧、摊销、薪酬、利息、税费 |
| 分析性复核 | 月度波动、毛利率、客户与供应商集中度 |
| 关联方识别 | 交易对手与关联方名单匹配 |
| 调整汇总 | 审计调整分录、试算平衡表、报表草稿 |

**建议先做：数据层 + 日记账测试 + 银行流水核对 + 往来款项**，覆盖面最广、最耗人工、也最容易验证效果。

## 三、准确性：如何识别数据问题、理解用户需求

### 结论

**不能"保证"，但比让模型直接看原始数据更可靠。** 模型逐行扫描几万条记录、做加总比对，正是它最容易漏和算错的地方。问题能否被发现取决于**跑了哪些测试**，风险从"模型看漏"转移到"测试设计是否完整"，后者可以由审计人员审查和补充。

### 识别数据问题

- **全量测试由代码做**：异常规则对全部数据执行，不抽样、不靠模型肉眼看。
- **测试库标准化**：按审计准则和所内程序整理成规则库，模型负责选择和设参数，不负责发明测试。
- **允许下钻**：模型看到异常清单后可调用查询工具，调取具体凭证、对方科目、前后期记录再判断。
- **结果可解释**：每个异常附命中规则、源数据行号和凭证号。

### 理解用户需求

- **需求映射到程序目录**：把用户的话对应到具体审计程序（如"查一下收入截止" → 截止测试），对应不上就追问。
- **执行前确认参数**：期间、科目范围、重要性水平、抽样方法，先展示给用户确认。
- **残余风险**：新型舞弊模式、需要职业判断的事项仍需审计人员复核。系统定位为提效，责任仍在审计人员。

### 底稿生成的验证

- 按小节生成（如余额核对 → 账龄分析 → 函证汇总 → 坏账测试 → 结论），每节一次独立调用。
- 每节生成后代码自动校验勾稽关系（明细合计 = 总账、本期发生额与余额变动一致等），不通过则重做。

## 四、跨项目通用性

**核心逻辑大部分可通用，参数和配置按项目调整。** 每个程序拆成：**通用代码 + 行业配置 + 项目参数**。

| 通用程度 | 程序 | 差异处理 |
|---|---|---|
| 基本通用 | 勾稽核对、重新计算、抽样方法、银行流水核对、账龄分析 | 导入新数据即可 |
| 通用但需调参 | 日记账测试、截止测试、分析性复核、函证 | 阈值、天数、敏感科目随重要性水平和客户规模变化 |
| 需按行业/项目定制 | 收入测试、存货、行业特有科目、不同项目类型（年审/IPO/专项/离任） | 按行业逐步积累配置 |

### 影响通用性的差异及对策

- **财务系统不同**（用友、金蝶、SAP 等）：由数据层导入适配器统一转换。
- **科目体系不同**：每个新项目建立"客户科目 → 标准科目"映射表，模型先自动匹配，人工确认。
- **会计准则不同**（企业会计准则、小企业准则、金融企业准则等）：规则库按准则区分。
- **所内底稿格式与程序要求**：所内统一，做一次即可。

### 新项目启动流程

1. 导入客户数据 → 适配器转换为标准结构
2. 生成科目映射建议 → 人工确认
3. 按行业加载默认配置
4. 按重要性水平自动计算项目参数 → 审计人员确认或微调
5. 开始按需执行各审计程序
