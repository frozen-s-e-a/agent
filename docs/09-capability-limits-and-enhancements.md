# 09 方案的能力边界与补充手段

**总体判断**：对目标场景（数据量大、流程固定的审计任务），01~08 的方案能解决大部分问题；但它解决不了"单步想不深"的问题，那是模型本身的上限。

---

## 一、各类问题的解决程度

| 问题 | 对应机制 | 解决程度 |
|---|---|---|
| 多重任务漏项 | 计划 + 覆盖检查 + 汇总步核对（03） | 大部分解决 |
| 长任务后半段变差、上下文丢失 | 每步干净上下文 + 固定锚点 + 按依赖引用（03、08） | 大部分解决 |
| 算错数、编造数字 | 代码计算 + 可追溯验证（05、08） | 基本解决 |
| 工具调错、格式错误卡住 | 约束解码 + 每步只给相关工具（08） | 基本解决 |
| 虚报完成、结果有瑕疵 | 代码验证（08 第 4.7 节） | 能用代码检查的部分解决；靠模型判定的部分只能缓解 |
| 慢 | 工作流减少调用、前缀缓存（08） | 部分解决；自由模式步骤多时总耗时可能增加 |
| 单步内推理不深（异常定性、波动原因解释、判断交易是否合理） | 无 | **解决不了**，拆得再细，每一步仍取决于模型自身能力 |
| 自由模式下拆解出错 | 覆盖检查 | 只能缓解；高频任务改走工作流才能根治 |
| 用同一个弱模型做判定 | — | 判定和执行容易犯同样的错，模型自检可靠性有限 |

**结论**：真正可靠的是**代码能检查的部分**。依赖模型判断的环节，需要下面的补充手段，最终靠人工复核兜底。

---

## 二、补充手段（在现有方案之上叠加）

按性价比排序。

### 1. 用非大模型的方法做异常识别

找数据问题本来就不是大模型的强项。以下方法在全量数据上更快、更稳定、结果可复现：

| 方法 | 适用 |
|---|---|
| 规则 | 周末记账、期末大额、整数金额、敏感科目组合等（05 日记账测试） |
| 本福特定律 | 金额首位数字分布异常 |
| 重复检测 | 重复凭证、重复付款、相同金额相同对象短期内多次发生 |
| 统计离群值 | 金额、频次、毛利率等明显偏离同类 |
| 孤立森林等无监督模型 | 多维特征组合下的异常交易 |
| 时序分析 | 月度波动、截止前后异常集中 |

模型只负责**解释**这些方法找出的异常，并给出建议定性。

**落地位置**：作为程序库（05）中的审计程序实现，输出统一的异常清单格式。

### 2. 动态示例库

把审计人员确认过的成功案例存起来，每次调用时检索 2~3 个最相似的案例放进提示词。弱模型照着示例做，比照着规则做准确得多，成本也低。

| 调用角色 | 示例内容 |
|---|---|
| router | 用户原话 → 映射到的程序 |
| extractor | 约束原文 → 参数 JSON |
| analyst | 异常 + 下钻结果 → 定性与理由 |
| writer | 小节数据 → 所内风格的底稿说明 |

- **来源**：06 第十一节的复核反馈闭环。被人工确认或修改后的结果才入库，修改后的版本优先。
- **检索**：按程序 ID、科目、行业过滤，再按语义相似度排序。
- **预算**：示例占用计入上下文预算的检索槽位（04）。
- **注意**：入库前脱敏，避免把某个客户的信息带进另一个项目的上下文。

### 3. 在现有模型上做针对性微调

不换模型，用 LoRA 针对窄任务训练小适配器：

- 适合的任务：需求映射、参数抽取、异常定性建议、按所内风格写底稿说明。
- 部署：vLLM 等推理服务支持同一底座模型加载多个适配器，按调用角色切换（08 模型网关）。
- 前提：
  - 训练用的 GPU 资源
  - 每个任务几百到几千条高质量样本（来自示例库和复核记录）
  - 评估集（07），微调前后对比，并检查通用能力是否下降
- 时机：系统运行一段时间、积累了足够数据之后。

### 4. 关键判断多次采样

- 只用于高风险判断，如异常定性、是否需要扩大样本。
- 同一问题生成 3 次（可略微提高 temperature），结论一致才采纳，不一致交给人工。
- 会增加算力消耗，不要全面使用；在模型网关中按角色和节点开关。

### 5. 用强模型做设计，本地模型做执行

- 工作流定义、提示词模板、校验规则、评估题不含客户数据，可借助外部强模型离线编写和打磨。
- 审计手册原文能否外发，需遵守所内规定。
- 运行时只用本地模型。设计质量越高，运行时对模型能力的要求就越低。

### 6. 把人放在对的位置

- 参数确认、异常定性、底稿结论由人确认（06）。
- 系统定位为"把重复劳动做完、把需要判断的地方整理好交给人"，不追求全自动。
- 界面上明确区分"代码算出的结果"和"模型给出的建议"。

## 三、如何判断方案是否足够

用 07 的评估集回归，看改造后剩下哪些失败类型：

| 剩余失败主要是 | 下一步 |
|---|---|
| 配置、提示词、上下文问题 | 继续优化 07、08 中对应部分 |
| 漏项、格式、数字错误 | 检查验证器覆盖是否不足 |
| 单步推理错误 | 结构化改造已到头，启动第二节第 2、3 项，或重新评估模型 |
| 程序目录覆盖不到 | 扩充程序库和工作流 |

## 四、纳入实施路线的建议

| 补充手段 | 建议加入的阶段（08 第八节） |
|---|---|
| 非大模型的异常识别 | 阶段 3，与首批程序一起建设 |
| 动态示例库 | 阶段 4，与复核反馈闭环一起建设 |
| 关键判断多次采样 | 阶段 4，按评估结果决定是否开启 |
| 用强模型做设计 | 阶段 2 起，贯穿工作流和提示词编写 |
| LoRA 微调 | 阶段 5 之后，视数据积累和评估结果 |
