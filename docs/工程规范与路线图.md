## 2. 本机数据布局

应用设置、项目元数据、会话事件默认在 %LOCALAPPDATA%\AuditAssistant。用户业务根目录独立选择；新结果默认放该项目的 outputs/<runId>。

大批量缓存和 spill 使用可单独选择的本地缓存目录，按项目/数据版本/任务隔离。分卷发布暂存在目标同卷目录，校验后发布。源码仓库、研究原件、业务原始材料、缓存和正式结果各自分开。

开发和测试使用专用测试数据根目录，不能读写日常会话/项目状态。删除缓存只按登记清单和引用状态操作，不递归清空用户项目根目录。

## 3. 模块与协议

pnpm workspace 管理 TS 包；Python 包与锁文件由选定 Python 工具链管理。具体工具版本通过 P0 兼容测试后固定并记录；发布包携带所需运行时，不能要求用户机器已有开发环境。

模块边界见[主方案](项目方案.md)。schema 是交换格式的唯一真相，TS/Python生成类型或校验器不得手工分叉定义。IPC有协议版本、消息大小、请求ID、取消和背压。

两种处理模式以统一 ExecutionRequest/ExecutionResult 调用；业务模块不能根据UI组件名称决定引擎。规则版本统一，允许不同实现，但必须过同一验收集。

插件权限、任务预算、字段映射和规则参数分别建模；“没有账号限制”不能实现成所有工具无限资源访问。

## 4. Git与变更

main 保持已提交基线可复现；按模块采用 feature/fix/docs 分支或小提交。提交建议采用 docs(plan)、feat(router)、fix(file-ops) 等作用域，便于追踪。

变更前检查现有差异，禁止覆盖用户未提交内容。普通文档更新不改全局Git配置；提交使用已经配置的作者身份，没有身份时保留修改状态并说明，不虚构用户身份。

上游源码固定提交并保留许可证和来源说明；升级先在独立分支完成适配/数据迁移/故障回归。研究原始二进制、解包产物、真实底稿、凭据、build和artifacts不进入Git；脱敏研究结论及小型合成样例可以提交。

## 5. 验证分层

|层次|验证内容|
|---|---|
|文档/静态|链接、需求追踪、目录边界、差异空白、类型和依赖约束|
|业务单元|原规则口径、金额精度、字段映射、null/重复/边界、来源定位|
|迁移覆盖|原功能/子功能、参数、默认值、模板、外部依赖逐项对照，缺项阻止首版发布|
|契约|TS/Python schema、IPC版本、usage语义、大小与错误返回|
|集成|Harness→工具→worker→文件发布与恢复|
|双模式|相同输入/参数/规则在轻量与批量下结果一致，边界切换不重复|
|大规模|十万/百万/千万行，复杂全局算子、磁盘/内存预算|
|故障|杀worker、重启、磁盘满、文件锁定、MCP失联、插件回滚|
|桌面e2e|项目与授权切换、对话卡片、取消、设置、Token展示|
|安装|无系统Node/Python的清洁环境，中文/空格路径、升级和恢复|

单元测试不调用收费模型；模型流式错误和usage用契约样例验证。真实模型联调单独记录供应商、时间、模型及实际用量。

大数据夹具由固定种子生成并保存hash，不能把数GB样例提交Git。性能报告包括冷/热缓存、硬件、运行时、规则版本、时长、内存、磁盘、行数和校验和。

## 6. 开发阶段与先后依赖

P0–P4全属首版。M01–M16为施工工作包而非产品分期；新发现的功能追加到总账，不能遗漏或放入优化待办后提前发布。

|阶段|产物|退出标准|
|---|---|---|
|P0 全量盘点与验证|模块/模板/Skill清单、原入口与参数基线、一个迁移样例、上游与双模式验证|清单可追踪，未知用途进入问题台账，实际依赖明确|
|P1 产品结构|对话、项目、设置、受限桥接、业务命令与参数卡片|按新UI调用业务，账号/配额按此前要求移除|
|P2 兼容底座|Harness、worker、路由、轻量/批量引擎、文件事务、扩展协议|必要的兼容和稳定性测试通过|
|P3 全部业务迁移|M01–M16及追加项，逐项研究、实现、原行为对照和模板验证|全部原业务及其参数分支可用，不局限于四类核心能力|
|P4 全量验收与发布|完整流程、外部依赖、安装恢复、双模式、新旧差异闭环|全部首版业务项通过；没有未解决的功能缺项|
|第二阶段起 功能优化|规则增强、流程改善、新业务、性能专项和模板升级|独立需求、版本、回归与变更说明，保持迁移基线可追溯|

每个工作包按“原行为盘点 → 基线样例 → 兼容实现 → 双模式/依赖验证 → 新入口接入 → 参数/模板/输出对照 → 关闭迁移项”推进。可以先提供部分覆盖的内部测试包，但只能在总账完整验收后命名为首版全功能版。

不能把无法还原源码、外部服务不可用或模板复杂等困难转换成默认删减范围。变更计算口径的优化留到后续单独评估；首版必需的进程隔离、数据保护和等价批量执行按工程要求完成。

## 7. 构建和输出

后续脚本分别提供开发启动、类型检查、业务测试、双模式测试、性能基准、测试打包、正式发布。当前不提供假装能运行的空命令。

构建系统显式指定 build 和 artifacts 路径；每个产物记录 Git 提交/未提交状态、运行时、依赖锁文件、输入资源hash和目标架构。安装包不得携带整个研究目录或开发数据。

测试包明确版本和测试标识；正式分发再完成签名、依赖/许可证清单、SBOM、升级回滚与发布校验。是否实际发布由相应发布任务决定。

## 8. 设计决策摘要

- ADR-001：Electron + React/TS + Node + Python；UI和计算故障隔离。
- ADR-002：优先适配固定版本dsh；保留上游来源与小范围补丁记录。
- ADR-003：会话日志权威，索引投影可重建；项目/任务元数据另有明确事务所有者。
- ADR-004：允许反编译参考，按原行为验证后迁移；首版全功能覆盖，规则与业务口径优化后续进行。
- ADR-005：双模式共用接口和语义；轻量在预算内存中处理，大批量用列式数据与落盘计算。
- ADR-006：默认本地单机；远程执行预留，不能随批量模式自动上传。
- ADR-007：Token实际、上下文估算、费用估算分别展示；未知保留未知。

- ADR-008：首版全功能迁移为发布硬门槛；工作包只决定施工顺序，未知入口和依赖阻塞不得被默认为后续范围。
