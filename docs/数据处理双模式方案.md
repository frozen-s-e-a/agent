# 数据处理双模式方案

版本：v0.4；更新：2026-09-09。
本文件为实施设计，尚未执行容量或性能测试。主方案见[项目方案](项目方案.md)。

## 1. 两条执行路径

用户要求同时兼顾本地小批量和大批量，首版按“同一应用、两种执行策略”实现，不拆成两个无法共享结果的产品。

|项目|轻量本地模式 local-light|大批量模式 local-batch|
|---|---|---|
|使用目标|单个/少量文件、小范围清洗与审计、交互反馈|跨文件合并、大量明细、全局统计/关联、大量文档|
|执行器|独立 Python worker；预算内 pandas/解析器|受调度的 Python worker；DuckDB/Parquet|
|数据存储|允许预算内整表；保留输入快照描述和结果文件|有界分批读取；持久化标准分片及 manifest|
|启动成本|尽量不创建分析库和全量中间文件|允许先标准化，换取后续复用与可恢复|
|可靠性|步骤级恢复；单步失败可以重算|分片/文件/阶段恢复；全局算子按可重算阶段管理|
|资源控制|入场估算 + 单 worker 上限 + 峰值监测|内存、CPU、磁盘、任务、线程、在途批次统一预算|
|结果|预览/Excel/小文件|分页查询、摘要 Excel、分卷 CSV/Excel、完整 Parquet|
|网络|本地处理；模型请求按用户配置发送所需上下文|同样本地处理；切换模式不会自动上传原始数据|

自动为默认选择；项目可设偏好，任务也可手动指定。界面使用“轻量本地”“大批量”等业务可理解名称，数据库参数放高级设置。

### 1.1 首版迁移兼容要求

双模式是首版执行基础，不能成为缩减原业务或提前优化业务规则的理由。所有原功能保留明确入口；可流式计算的任务走等价批量算法，依赖完整工作簿/模板/外部服务的功能可由批量队列调度其兼容执行器，不强行改写为SQL。

首版优先核对原参数、默认值、金额/舍入、样本方法、输出顺序、公式、格式及宏行为。新增证据索引和调度记录使用旁路产物，不破坏原业务输出。原工具支持而当前适配器暂缺的格式，属于迁移待解决项，不能自动降为后续。

能力表逐功能记录轻量/批量执行方式、支持粒度、依赖和实测规模。结构上无须双引擎的操作（如文件打开）可共用同一实现，但功能必须可用。超预算可以明确报错或排队，不能静默跳过部分原操作。

## 2. 规模分级与路由

### 2.1 验证场景，不作为已实现性能承诺

|级别|合成测试场景|默认验证路线|验证重点|
|---|---|---|---|
|S 小批|1千、1万、5万行；少量文件；10–30列|轻量本地|启动成本、模板/公式处理、内存、结果精度|
|M 边界|10万行；窄表/宽表/长文本各一组|自动路由并强制两种模式对照|路由估算、升级执行、一致性|
|L 大批|100万行；10/100个文件；跨文件重复和关联|大批量|有界内存、全局正确性、缓存复用、恢复|
|XL 扩展|1000万行 Parquet/CSV，分散多文件|大批量|磁盘溢写、倾斜数据、全局算子和分卷结果|
|D 文档|100/1000份文件；文本 PDF 与扫描件分开|逐文件/逐页队列|解析/OCR并发、失败隔离、证据定位|

列宽、类型、压缩率、关联基数和 OCR 成本会改变资源需求。千万行测试不放进一个 Excel 工作表，也不把行数等同于可用容量。

### 2.2 决策输入

execution-router 先生成 WorkloadProfile：文件清单/大小、格式、工作表和行列估计、样本行内存、解压体量、规则算子、输出规模估计、可用 RAM/磁盘和项目偏好。

初始可配置参数草案，P0 测量后固定：

- 轻量候选：通常不超过 5 万行、少量文件，且估算的整个执行峰值不超过轻量预算；这些数量是路由提示而非强制功能配额。
- 轻量估算必须计入解析对象、字符串、DataFrame 副本、关联中间结果及导出缓存，不只计算源文件字节。
- 轻量峰值预算初始取 512 MiB 与本次计算内存预算的 25% 两者较小值；超宽表或复杂连接可在更少行时转批量。
- 大批量需要先估算磁盘空间；本机不够时允许改缓存盘、减少选定输入、顺序运行或取消，不自动使用云端。
- 抽样估算不充分的输入标注低置信度，采用更保守路径；运行中仍监测实际峰值。

StrategyDecision 保存 requestedMode、selectedMode、reason、estimate、limits、inputSnapshot、planVersion。用户可看选择原因，但不能强制跳过已触发的硬资源保护。

### 2.3 切换语义

轻量越过预算时，停止未提交步骤、回收 worker，确认输入快照未变后启动批量路径。切换使用同一个逻辑 taskId、新的 attemptId，明确显示“已转大批量处理”。

已经生成并发布的底稿不重复写入。只有具备恢复/幂等契约的任务允许自动切换；其余任务保留中间记录并给出可执行恢复方案。批量到轻量不迁移正在运行的查询，只在下一步骤或新任务重新选择。

## 3. 共同规则与接口

同一规则由 audit-domain 定义语义：字段、类型、参数、null 处理、金额精度、分组键、排序、阈值边界、输出和证据。可分别提供轻量 Python 实现与批量 SQL 实现，但共用规则编号、版本和验收用例。

任务示意字段：

~~~json
{
  "taskId": "task-example",
  "mode": "auto",
  "inputRefs": ["dataset-example"],
  "inputVersion": "sha256-example",
  "ruleSet": {"id": "ledger-checks", "version": "1"},
  "parameters": {"currency": "CNY", "amountScale": 2},
  "limits": {"memoryMiB": 2048, "threads": 2},
  "outputPolicy": "new-artifacts"
}
~~~

这是契约示意，不是当前已可调用 API。金额 scale 是业务显式参数，不预设所有币种/税率/数量都只有两位小数。

结果统一返回：完整性状态、数据集版本、规则版本、摘要、行数、异常数量、证据引用、文件引用、警告和资源统计。样本预览必须有 preview 标记、总量和分页信息。

## 4. 轻量本地处理

流程：探测输入 → 校验字段 → 预算内读取 → 执行规则 → 验证行数/金额等不变量 → 暂存输出 → 统一发布。

- 小表可用 pandas 直接计算；禁止无预算地递归加载目录和累积 DataFrame。
- Excel 读取保留原工作表/行号。模板格式、合并单元格和公式需要单独测试；读取公式缓存不等于重新计算公式。
- 少量 PDF 按页处理，可在预算内合并提取结果；OCR 是独立可取消工具，先确认实际需要。
- 不强制建 DuckDB 数据库和持久化 Parquet；仍保存输入 hash、参数、规则版本、任务状态和输出 hash。
- 长计算也在 worker 中完成，小模式同样不能阻塞 UI。出现解析错误与预算不足时按统一错误协议返回。
- 恢复可从已完成工具边界开始；内存中的中间表不能声称在崩溃后仍然存在。

## 5. 大批量导入与标准化

### 5.1 格式适配

|格式|读取策略|注意事项|
|---|---|---|
|CSV/TSV|流式解析，显式编码/分隔符/schema，批次写入 Parquet|引号内换行、坏行、混合类型；不能按文本换行粗暴分块|
|XLSX|可用 read-only 行迭代；逐表、逐文件导入|共享字符串、样式和压缩体量仍会影响内存；工作表尺寸可能错误|
|Parquet|按列/分区扫描，尽量下推过滤|校验 schema、精度和分区版本|
|XLS/XLSB|独立兼容适配器，先验证支持范围|不假设每个库都支持真正流式读取；超预算可要求转换或受控转码|
|PDF/图片|逐文件/逐页提取，OCR 独立队列|页图像像素预算、密码文件、坏页和人工复核|

openpyxl 提供 read-only 和 write-only 模式，但它们有不同功能限制；本项目需测试具体文件结构，不能直接承诺整个应用恒定内存。[openpyxl 官方说明](https://openpyxl.readthedocs.io/en/stable/optimized.html)

### 5.2 分片与来源

批次以字节预算为主、行数为辅，初始目标 8–32 MiB 的批次负载；解析器和对象附加内存另外计算。限制在途批次数，消费者慢时读取暂停，不能无限排队。

每个标准分片记录 sourceId、fileHash、sheet/page、原始行标识、schemaVersion、转换版本、accepted/rejected 行数、金额等控制合计。路径变化不改变证据内容身份。

Parquet 分片使用显式 schema，保留字符串代码和定点金额；文件较多时通过合并分片控制小文件数量。分区按经验证的实体/期间等键设计，避免每个唯一凭证生成一个文件。

原始行数必须等于成功接收、拒绝和按明确规则排除的行数之和；合并表头、重复表头、空行等排除项有原因和数量。坏行进入错误集，可修复后产生新版本，不静默丢弃。

## 6. 大批量计算正确性

|计算类型|实现路线|不允许的捷径|
|---|---|---|
|逐行校验|批次计算，汇总错误分片|每个批次都保留在内存等待最后合并|
|求和/分组|DuckDB 全局聚合或可合并的精确中间状态|把批次均值再取平均|
|去重/唯一性|全局键聚合或完整哈希分区；保留稳定行身份|只在单文件或单批次内去重|
|跨表核对|显式键和关联基数；先检查重复键与预计输出量|盲目多对多连接造成结果爆炸|
|排序/窗口|允许落盘的全局执行或键完整的分区计算|直接拼接各批次排序结果|
|抽样|保留原总体、策略和顺序约定；记录可获得的随机状态，原支持固定种子时沿用|每批随机抽样后声称等同整体抽样，或为可复现而擅改原抽样方法|
|金额/勾稽|Decimal/定点精度、币种分组、溢出和舍入检查|二进制浮点直接作为最终金额一致性依据|

首次实现以一个批量执行器负责全局算子，减少重复调度和跨进程共享可写数据库。未来并行分区时，必须证明边界键完整或增加归并步骤。

模型可以提出规则或查询请求，但数据访问只允许注册数据集/受控查询计划。自定义 SQL 需做语法、数据源、操作和资源校验；不能仅凭 SELECT 字符串开头就判断没有文件/网络副作用。

## 7. 资源预算与调度

资源设置属于项目/应用设置。默认优先稳定和桌面可用性，P0 再调整参数：

|资源|初始策略|监控与退路|
|---|---|---|
|内存|主机先为系统和交互保留 max(4 GiB, 物理内存25%)；再结合当前可用量分配作业|同时监测 RSS/提交内存，低余量停止新增任务|
|大作业并发|默认 1 个重任务；多个项目公平排队|支持手动调整但必须通过预算入场|
|查询线程|初始 min(4, max(1, 逻辑核数-2))，与并发共享 CPU 配额|OCR、BLAS、DuckDB 不各自占满全部核心|
|批次|按目标字节大小；有界队列|背压、回收已提交批次|
|磁盘|用户可选本地暂存盘；为输出、Parquet、spill和备份分开预算|低空间停止新写入，保留检查点与清理入口|
|查询|超时、取消、行数/输出大小和中间结果预算|复杂全局操作改写、分阶段或明确报资源不足|

上述公式是默认策略草案，不能超出现有空闲资源；极低配置可以拒绝大作业并解释缺口。DuckDB 的 memory_limit、temp_directory、max_temp_directory_size 由作业预算生成，不能让每个子进程都按全部机器资源分配。

memory_limit 不是整个 Python/原生库进程的绝对上限。进程级监测、停止新任务和受控终止是必要补充；终止后产生 failed/interrupted 状态，不能出现成功报告。网络盘不是默认 spill 位置。

磁盘估算通过小样本实测展开率、分片大小、查询计划和输出规模给出范围；不固定假设“源文件乘二就够”。每个目录的剩余空间与计划使用量都需检查。

DuckDB 官方对流式执行、磁盘溢写和内存限制有说明；仍存在无法溢写的资源失败情形。[内存管理](https://duckdb.org/2024/07/09/memory-management)、[查询调优](https://duckdb.org/docs/current/guides/performance/how_to_tune_workloads)

## 8. 检查点、缓存和恢复

manifest/checkpoint 至少绑定：

~~~text
taskId / attemptId / phase
source hashes / schema / mapping / rule / engine versions
completed partitions with hashes and row counts
current stage / output publication state / resumability
~~~

- CSV/Excel 原始读取可能只能从文件或工作表开头重放；已提交 Parquet 分片可复用，但需要稳定位置标识防止重复写入。
- Parquet 可按已登记分片/行组重新计划；任意长 SQL 在进程崩溃后通常重启该查询阶段，不能承诺从内部任意算子恢复。
- 已完整计算并验证的阶段可复用；中途半写分片不进入 manifest，也不参与最终计算。
- 源文件、映射、规则、参数或影响语义的引擎版本改变时失效相关缓存，创建新数据集版本。
- 恢复结果必须与同一输入从头运行一致。恢复时间、重读数据量和重复计数都纳入测试。
- 缓存按项目隔离、版本识别；清理只删除应用登记且无活动引用的缓存，不能删除原文件、正式结果或研究证据。

## 9. 大结果展示与模型上下文

UI 显示阶段和汇总：文件总量/成功/失败、处理行数、预计/实际资源、完成产物。总量未知时用已处理数量和当前阶段，不能伪造百分比或 ETA。

服务端分页，前端使用虚拟列表；IPC 返回引用和有界页，事件不含全表。诊断日志有轮换/容量限制，进度可采样，但结果、失败和发布事件需要持久记录。

模型只接收 schema、数据质量统计、聚合结果、受限异常样本和证据引用。每次工具返回均有大小/Token 预算与截断标记；对更多证据可分页取数。抽样解释不能表述为已完整核查所有数据。

两种模式都允许直接查看相同格式结果；模式改变不影响证据引用和用户复核状态。

## 10. 导出与证据

完整结果以 Parquet/分卷 CSV 保存；工作底稿可输出 Excel 摘要、异常明细分卷、证据索引和 run manifest。轻量模式直接产生小型工作簿，同样经过验证与发布。

Excel 单工作表最多 1,048,576 行、16,384 列；分卷容量须扣除表头，并避免超限单元格和样式。超大编号以文本导出，防止被 Excel 数字精度截断。[Microsoft Excel 限制](https://support.microsoft.com/en-us/excel/excel-specifications-and-limits)

导出分两类：纯数据流式写入与复杂模板填充，分别实现；write-only 模式不能当作任意单元格编辑器。长文本完整值保留在可承载的旁路结果中，Excel 预览明确提示。

一个 run 可能包含多个文件，manifest 记录各卷 schema、行区间、行数、hash、控制合计和完成状态。验证通过才发布“完整结果”；仅部分成功时显示 incomplete 和缺失清单。不要先宣布成功再后台补齐文件。

## 11. 性能与一致性验证

P0 记录实测机器：CPU、RAM、磁盘/文件系统、OS、运行时、库版本、数据集 hash 和冷/热缓存条件；当前没有用户硬件配置，因此以下是测试条件草案而非推荐采购配置。

- 参考环境草案：Windows x64、16 GiB RAM、本地 SSD；8 GiB/32 GiB 作为不同预算回归点，实际值写入报告。
- S/M：强制两条路径运行相同样本，对比排序归一后的结果、金额、null、重复键、证据位置和错误行。
- L：100万行至少覆盖导入、全局重复、月度汇总、跨表勾稽和导出，测总时长、各阶段时长、RSS/提交内存、spill、磁盘峰值和恢复开销。
- XL：1000万行记录需覆盖超内存聚合/排序、倾斜键和大输出；公布各算子支持结果，不以一条 COUNT 查询宣称全部支持。
- D：纯文本 PDF 与 OCR 分别测文件/页吞吐、并发内存和坏页隔离。
- 故障注入：worker 被杀、磁盘满、文件锁定、输入变更、应用重启、取消、坏 CSV、错误 Excel 尺寸、长文本、重复请求。
- 路由测试：小文件高展开率应进入批量；简单少量输入应走轻量；切换不能重复发布或改变计算结论。

发布硬门槛是结果准确、无静默丢行、无原件损坏、不会拖垮 UI、资源不足可解释且可以恢复。吞吐/耗时目标由 P0 测量后在同版本基准中固定，不能在未运行之前填写“已支持千万行”。

## 12. 未来远程执行边界

首版两种模式都在本机。远程 worker 是 execution adapter 的后续实现，需要另行定义传输、授权、数据驻留、成本和任务恢复；不在当前“大批量”开关下隐式启用。先验证本地引擎再决定是否确有分布式需求。
