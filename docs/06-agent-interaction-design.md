# 06 Agent 层交互设计

本文细化 Agent 层：从用户提出需求，到映射审计程序、确认参数、执行、解读结果、下钻核查，再到复核反馈的完整交互。

**设计目标**
- 准确理解用户要做哪项审计工作，理解不了就追问，不猜。
- 尽量少问：能从项目档案、行业配置、数据本身得到的不问。
- 每次模型调用只做一件小事，输出结构化结果，由代码串联流程。
- 审计人员始终掌握关键决定：参数、异常定性、底稿结论。

---

## 一、整体流程

```
用户需求
  │
  ▼
① 意图抽取 ──► ② 程序映射 ──► ③ 参数补全 ──► ④ 前置检查
                  │ 低置信            │ 缺关键参数      │ 不满足
                  ▼                   ▼                 ▼
               追问/候选           追问             提示或补跑前置程序
                                      │
                                      ▼
                              ⑤ 执行确认卡（按风险决定是否需要确认）
                                      │
                                      ▼
                              ⑥ 执行（规划→执行→验证，见 03）
                                      │
                                      ▼
                              ⑦ 结果解读 ──► ⑧ 下钻核查（可多轮）
                                      │
                                      ▼
                              ⑨ 输出底稿/结果 ──► ⑩ 人工复核与反馈
```

每个环节的状态都写入**会话工作区**，后续对话可以引用（见第九节）。

---

## 二、项目档案（减少追问的基础）

每个审计项目维护一份项目档案，作为参数的默认来源，Agent 每次调用时自动读取。

```yaml
project:
  client: 某某制造有限公司
  industry: 制造业
  engagement_type: 年度财务报表审计
  period: 2025-01-01 ~ 2025-12-31
  standard: 企业会计准则
  materiality:
    overall: 5000000          # 整体重要性
    performance: 3750000      # 实际执行的重要性
    trivial: 250000           # 明显微小错报临界值
  data_status:
    ledger: imported          # 序时账
    trial_balance: imported   # 科目余额表
    bank_statements: partial  # 银行流水（缺 2 个账户）
    mapping: confirmed        # 科目映射已确认
  related_parties: [...]      # 关联方名单
  notes: "存在外销业务，收入确认以报关单为准"
```

档案由项目启动流程建立（见 05 第四节），审计人员可随时修改；Agent 发现信息缺失时提示补充，而不是在每个任务里重复询问。

## 三、程序目录（需求映射的依据）

每个审计程序在目录中有一条结构化定义。目录是**需求理解的边界**：Agent 只能执行目录中的程序，不临时发明测试。

```yaml
- id: JE_TEST
  name: 日记账测试
  aliases: [分录测试, 凭证测试, 异常分录, journal entry, 筛凭证, 查异常凭证]
  scope: 全部科目，可限定科目范围
  requires_data: [ledger, trial_balance]
  prerequisites: [LEDGER_TB_RECONCILE]        # 序时账与余额表勾稽通过
  params:
    period:        {required: true,  default_from: project.period}
    accounts:      {required: false, default: all}
    amount_threshold: {required: true, default_from: project.materiality.performance, rule: "×0.5"}
    rules:         {required: false, default_from: industry_config.je_rules}
    period_end_days: {required: false, default: 5}
  side_effects: none                           # 只读
  outputs: [summary_table, exceptions, workpaper_section]
  risk_level: low                              # 决定是否需要执行前确认

- id: AR_CONFIRMATION
  name: 应收账款函证
  aliases: [发函, 函证清单, 询证函, 往来函证]
  requires_data: [ledger, trial_balance, aux_customer]
  prerequisites: [AR_AGING]
  params:
    selection_method: {required: true, options: [金额门槛, 全部, 抽样], default: 金额门槛}
    threshold:     {required: true, default_from: project.materiality.performance}
    include_zero_balance_with_activity: {required: false, default: true}
  side_effects: produces_formal_sample         # 产生正式样本
  risk_level: high
```

关键字段说明：
- **aliases**：常见叫法和口语表达，用于映射；人工纠正后会持续补充（见第十节）。
- **requires_data / prerequisites**：用于前置检查。
- **params.default_from**：参数默认值来源，减少追问。
- **side_effects / risk_level**：决定是否需要执行前确认。

## 四、需求理解：意图抽取与程序映射

### 4.1 意图抽取（一次模型调用，结构化输出）

模型只做抽取，不做判断和执行。

```json
{
  "tasks": [
    {
      "action": "账龄分析",
      "account": "应收账款",
      "period": null,
      "constraints": [],
      "deliverable": "底稿"
    },
    {
      "action": "函证清单",
      "account": "应收账款",
      "constraints": ["余额大于50万的全部发函"],
      "deliverable": "清单"
    }
  ],
  "unclear": []
}
```

- 一句话中有多项工作时拆成多个 task，避免漏项。
- 原话中的数字、科目、条件原样保留在 constraints 中，供后续转换为参数。
- 模型无法确定的内容写入 `unclear`，不自行补全。

### 4.2 程序映射（代码 + 模型）

1. **规则匹配**：用 aliases 和科目做关键词匹配，得到候选程序。
2. **检索补充**：候选为空时，用程序描述做向量或关键词检索取 top-3。
3. **模型选择**：把 task 和候选程序（只给名称和一句话描述）交给模型，输出选择和置信度。

| 置信度 | 处理方式 |
|---|---|
| 高（唯一明确匹配） | 直接进入参数补全 |
| 中（2~3 个候选） | 展示候选让用户选，附一句话说明区别 |
| 低（无合适候选） | 追问用户想做什么；仍无法映射则明确告知"目前不支持该程序"，并记录到需求池 |

### 4.3 多任务依赖

多个 task 映射后，按程序目录中的 `prerequisites` 自动排序。例如函证依赖账龄分析，则先执行账龄分析；若用户只要求函证，也会提示"将先执行账龄分析"。

## 五、参数补全与确认

### 5.1 参数来源优先级

```
用户本次明确说的 > 本会话之前确认过的 > 项目档案 > 行业配置 > 程序默认值
```

每个参数记录来源，在确认卡中展示，便于审计人员判断是否需要修改。

### 5.2 约束到参数的转换

用户的自然语言约束由模型转换为参数，再由代码校验：

| 用户原话 | 转换结果 | 代码校验 |
|---|---|---|
| "大于 50 万的都发" | threshold = 500000, selection_method = 金额门槛 | 数值合法；与重要性水平比较，过高时提示 |
| "只看第四季度" | period = 2025-10-01 ~ 2025-12-31 | 在审计期间内 |
| "收入和应收" | accounts = [主营业务收入, 应收账款] | 科目在映射表中存在 |

校验不通过时，把问题告诉用户，而不是静默使用默认值。

### 5.3 是否需要执行前确认

| 情况 | 处理 |
|---|---|
| 只读、可快速重跑、参数全部来自默认或用户明说 | 不确认，直接执行，结果中列出所用参数 |
| 参数中有模型推断的值 | 确认卡展示推断项，其余项折叠 |
| 产生正式样本、写入底稿、覆盖已有结果、耗时较长 | 必须确认 |

确认卡示例：

```
即将执行：应收账款函证清单
  期间          2025-01-01 ~ 2025-12-31      来源：项目档案
  选样方式      金额门槛                      来源：您的要求
  门槛金额      500,000                       来源：您的要求
  零余额有发生额的客户  纳入                  来源：程序默认   [修改]
  前置程序      应收账款账龄分析（将先执行）
[确认执行]  [修改参数]  [取消]
```

## 六、追问策略

- **只问影响结果的缺失项**：能用默认值且影响不大的，不问，在结果里注明。
- **能从数据得到的不问**：例如"有哪些银行账户"直接查数据。
- **一次最多 3 个问题**，每个问题带选项和建议默认值。
- **问题要具体**：说明为什么问、不同答案会导致什么差异。
- **无人回应时**（后台任务或超时）：采用建议默认值继续，在结果顶部标注"以下参数为默认取值，请复核"；但会产生正式样本或覆盖结果的操作暂停等待。

示例：

```
需要确认一点：函证门槛您说的是"大于 50 万"，项目的实际执行重要性为 375 万。
按 50 万选样会选出 86 家客户，覆盖余额 92%。
  A. 按 50 万执行（建议）
  B. 改为按实际执行重要性 375 万（选出 12 家，覆盖 71%）
  C. 其他金额
```

## 七、前置检查

执行前由代码检查，不消耗模型调用：

| 检查项 | 不满足时 |
|---|---|
| 所需数据是否已导入 | 告知缺哪些数据、需要的格式，提供导入入口 |
| 科目映射是否已确认 | 列出未映射的相关科目，请用户确认或由模型给出建议后确认 |
| 前置程序是否已执行且通过 | 自动加入执行计划；若前置程序勾稽失败，暂停并展示差异 |
| 数据期间是否覆盖参数期间 | 告知缺失的月份 |

## 八、执行中交互

- 执行采用 03 中的规划→执行→验证循环，客户端实时展示步骤和进度。
- **暂停条件**（需要人工判断时主动停下）：
  - 勾稽差异超过明显微小错报临界值
  - 异常数量远超预期（如超过总笔数的 5%），可能是参数或数据问题
  - 数据质量问题（大量空值、重复凭证号、借贷不平）
- 用户可随时中断、修改参数后从当前步骤重跑。

## 九、结果解读与下钻

### 9.1 结果呈现结构

每个程序的结果按固定结构呈现，模型只基于汇总表和异常清单撰写：

1. **结论摘要**：一到三句话，说明执行了什么、主要发现。
2. **关键数字**：覆盖金额、覆盖比例、异常笔数和金额（由代码计算填入，不由模型生成）。
3. **异常分级**：按金额和规则严重度分为"需重点关注 / 需进一步核查 / 低风险"。
4. **建议下一步**：如对某几笔执行凭证检查、扩大样本、补充函证。

### 9.2 下钻工具集

模型解读异常时可调用以下只读工具，每次结果都经过截断后进入上下文：

| 工具 | 用途 |
|---|---|
| query_voucher | 按凭证号取完整凭证（全部分录行） |
| query_counterpart | 查某笔分录的对方科目及金额 |
| query_account_period | 查某科目某期间的发生额和余额变动 |
| query_by_party | 查同一往来单位的全部交易 |
| query_adjacent | 查期末前后若干天同类交易（截止测试） |
| query_prior_year | 查上年同期数据（需已导入） |

- 单个异常的下钻轮数设上限（如 5 次），超过则标记为"需人工核查"。
- 下钻得出的判断必须引用工具返回的具体凭证号和金额，不能只给结论。

### 9.3 异常定性由人确认

模型对每个异常给出**建议定性**（已合理解释 / 需关注 / 需执行进一步程序）和理由，审计人员确认或修改后才计入底稿结论。

## 十、会话状态与结果引用

- 每次程序执行生成一个**结果 ID**（如 `R-JE-003`），每条异常有序号（如 `R-JE-003#17`）。
- 用户说"刚才第 17 条"、"上一个结果里金额最大的那几笔"时，Agent 通过结果 ID 和代码查询定位，不依赖模型记忆。
- 会话工作区保存：已确认的参数、已执行的程序及结果 ID、异常定性状态、待办事项。每次调用只把与当前任务相关的部分放入上下文。
- 上下文压缩时，结果本身留在工作区，上下文中只保留"结果 ID + 一句话摘要"。

## 十一、复核与反馈闭环

| 反馈类型 | 记录位置 | 用途 |
|---|---|---|
| 用户纠正了程序映射 | 程序目录 aliases 候选池 | 定期审核后补充别名，提高映射准确率 |
| 用户修改了默认参数 | 项目档案 / 行业配置候选 | 同类项目参数默认值调整 |
| 异常定性被推翻 | 规则反馈库 | 调整规则阈值，减少误报 |
| 用户提出目录外需求 | 需求池 | 决定后续开发哪些程序 |

反馈先进入候选池，由负责人审核后生效，避免个别项目的特殊设置污染通用配置。

---

## 十二、模型调用切分

每次调用只做一件事，使用结构化输出，便于代码校验。

| 环节 | 模型任务 | 输入（上下文） | 输出 |
|---|---|---|---|
| 意图抽取 | 拆分任务、保留原始约束 | 用户原话 + 最近 2 轮对话摘要 | tasks JSON |
| 程序选择 | 从候选中选择 | task + 候选程序简述 | 程序 ID + 置信度 |
| 约束转换 | 自然语言约束转参数 | 约束原文 + 参数定义 | 参数 JSON |
| 追问生成 | 写清楚问题和选项 | 缺失参数 + 影响说明 | 问题文本 |
| 结果解读 | 写结论摘要与异常分级理由 | 汇总表 + 异常清单（截断） | 结构化解读 |
| 下钻判断 | 决定查什么、给出建议定性 | 单条异常 + 下钻结果 | 工具调用 / 定性建议 |
| 底稿说明 | 写分析说明与结论 | 小节数据 + 模板要求 | 文本段落 |

不交给模型的事：数值计算、筛选、汇总、勾稽、参数合法性校验、程序依赖排序、结果 ID 查询。

---

## 十三、边界与明确告知

以下情况 Agent 应直接说明，而不是勉强完成：

- 需求无法映射到已有程序
- 所需数据缺失且无法替代
- 需要职业判断的事项（如重要性水平的最终确定、审计意见类型、是否存在舞弊），Agent 只提供数据支持和参考，不给结论
- 前置程序勾稽不通过

## 十四、完整示例

> **用户**：帮我把应收账款的账龄分析和函证清单做一下，大于 50 万的都要发函。

1. **意图抽取**：两个 task，账龄分析、函证清单；约束"大于 50 万都发函"。
2. **程序映射**：AR_AGING（高置信）、AR_CONFIRMATION（高置信）。
3. **依赖排序**：函证依赖账龄分析，顺序为 AR_AGING → AR_CONFIRMATION。
4. **参数补全**：期间、科目映射来自项目档案；threshold = 500000 来自用户。
5. **前置检查**：序时账、余额表、客户辅助核算已导入；映射已确认；通过。
6. **风险判断**：函证产生正式样本，需要确认。门槛远低于实际执行重要性，在确认卡中提示选样数量和覆盖率。
7. **用户确认**后执行：账龄分析 → 勾稽（明细合计 = 总账余额）→ 函证选样 → 生成清单。
8. **结果解读**：
   - 账龄：3 年以上余额 420 万，集中在 2 家客户。
   - 函证：选出 86 家，覆盖余额 92%；其中 3 家为关联方，另 5 家期后无回款。
   - 建议：对 3 年以上的 2 家客户执行下钻核查。
9. **用户**："看下账龄最长那家是什么情况。"Agent 调用 query_by_party，返回近两年交易和回款记录，给出建议定性及凭证号依据。
10. **输出**：账龄分析底稿小节、函证清单 Excel，参数和来源附在底稿首页。
