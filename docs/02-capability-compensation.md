# 02 在不换模型的前提下补偿模型能力

**核心思路：把"想全、想对"从模型脑子里搬到代码结构里。** 模型每次只做一个小而明确的动作，其余交给流程约束。

## 一、思考更严谨（收益最大）

1. **规划与执行分离**：独立调用产出 3~7 步 JSON 计划，再逐步执行。每步只给当前步骤、上一步结果摘要和必要文件。
2. **代码强制验证**：每步结束自动校验（测试、lint、读回文件、勾稽核对），失败把错误原样喂回重试，设上限（如 3 次）后升级或报 blocker。
3. **自检轮**：最终答复前，对照原始需求逐条核对"做了什么、漏了什么"，对多重任务漏项特别有效。
4. **任务清单常驻**：todo 状态放在每轮上下文固定位置，模型不需要"记得"还剩什么。
5. **流程模板**：常见任务写成固定流程，模型只填空。
6. **多采样投票（可选）**：仅用于高风险决策，生成 2~3 个方案再比较选择。

## 二、输出更流畅

1. **流式输出 + 进度可视化**：思考、工具调用、结果分别流式展示，长任务显示当前步骤。
2. **并行化**：无依赖的工具调用、子任务并行执行。
3. **前缀缓存**：固定 system prompt 和工具描述放最前且不变，降低首字延迟（需推理服务支持）。
4. **精简上下文**：工具输出先截断或摘要，上下文越短越快越准。
5. **格式容错层**：JSON 修复或约束解码（grammar / JSON schema），消灭"卡住、重来"。
6. **推测性预取**：常见的读文件、检索由代码提前准备。

## 三、客户端功能与体验

- 可中断、可续跑、从某一步重来
- 计划视图：展示计划和每步状态，允许编辑后再执行
- 审批与 diff 预览：改文件、执行命令前确认
- 会话管理：历史、分支、压缩摘要可查看，任务可后台运行
- 失败可解释：显示卡在哪一步、为什么、建议怎么办
- 模板和快捷指令：常见任务一键入口

## 落地顺序

1. **先做**：工具输出截断、JSON 容错/约束解码、流式和进度展示（成本低、见效快）
2. **再做**：规划与执行分离、每步验证、任务清单（能力提升核心）
3. **最后做**：自检轮、多采样、流程模板、客户端高级功能

## 先建立评估基准

收集 10~20 个真实失败任务，记录每个是**哪一步坏的**：漏子任务、工具参数错、上下文丢失，还是推理错误。用它决定优化优先级，并作为改造前后的对比基准。
